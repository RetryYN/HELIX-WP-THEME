## 新発見

| 発見 | 影響 | AGENT NEO反映 |
|---|---|---|
| `seo-tool/v1` と `aseo/v1` のnamespace差分 | Automation SEO連携を固定URL前提にすると壊れる | `/wp-json/` discovery、capability probe、version endpointを必須化 |
| 実運用ThemeBのSEO 100 / mobile performance 95 | ThemeB設計より、軽い運用テンプレートとプラグイン選定が強い | 法人LP基盤ではテーマ標準の画像/JS予算を設ける |
| テーマA実運用はh1が検出されずJSON-LD 0 | SEOテーマでも運用設定/トップ構成で出力が欠落し得る | SEO監査をテーマ設定に閉じず、DOM実測で検出 |
| ローカルThemeBはcanonical falseだった | WP設定/テーマ切替直後の状態にSEO出力が依存 | テーマ初期化時のSEO smoke testを必須化 |
| 実運用テーマAはconsole error 4 | 表示上動いていても運用JSエラーが残る | Playwright console監査を週次観測へ入れる |

## セキュリティ・運用観点

公開REST indexにAI write/media/update系route名が見えること自体はWordPressでは一般的にあり得る。ただし、route名が攻撃者にも機能推測を与えるため、以下は必須。

| 項目 | 必須対応 |
|---|---|
| write系route | `current_user_can`、nonce/application password、監査ログ、dry-run、rollback |
| media upload | MIME/サイズ制限、権限分離、添付先post制約、ウイルス/拡張子検査 |
| update/apply | 管理者権限だけでなく操作スコープ、署名済みjob、二段階承認 |
| public tracking | rate limit、bot除外、PII非保存、CORS制限 |
| WP-Cron | 重要処理はsystem cron/queueへ逃がす。WP-Cronは補助に留める |
| Debug | `WP_DEBUG_DISPLAY=false` は維持。warningはログ監視で検出し、UI破損前に修正 |

## AGENT NEO設計反映

1. テーマ本体はThemeB型の機械可読契約を採用する。`block.json`、`theme.json`、section metadata、REST discovery、CPT/API schemaを標準化する。
2. SEO出力思想はテーマA型を取り込む。title/description/canonical/noindex/OGP/JSON-LDはテーマ内で初期保証し、SEOプラグイン導入時は衝突検出を行う。
3. 実運用速度は「テーマの軽さ」だけでは決まらない。画像数、スライダー、商品カード、RTOC、計測タグを含めたページ予算を設計に入れる。
4. Automation SEO連携はnamespace固定にしない。`/wp-json/` からversion、capability、schemaを発見し、write操作はdry-runを先に実行する。
5. AIエージェント向けにはDOMに `data-agent-section-id`、`data-cta-id`、`data-template-part`、`data-conversion-role` を持たせ、LLMO/引用/更新対象を安定化する。
