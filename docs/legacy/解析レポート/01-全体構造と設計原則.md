# 全体構造と設計原則

## 観測した構造

参照テーマは `functions.php` を起動層にして、主要機能を `lib/`、`classes/`、`parts/`、`src/gutenberg/blocks/`、`build/` に分離している。新規テーマでもこの「薄い起動層 + 機能別モジュール」の設計は取り込む価値が高い。

| 領域 | 観測内容 | 設計に生かせる点 |
|---|---|---|
| `functions.php` | 環境チェック、定数定義、autoload、主要lib読み込み | 起動順を明確にし、AIが変更範囲を把握しやすくする |
| `lib/` | WordPressフック、CPT、REST、カスタマイザー、読み込み制御 | WP統合処理を責務別に分ける |
| `classes/` | 設定データ、管理画面、スタイル生成、ユーティリティ | 状態管理と表示処理を分離する |
| `parts/` | header、footer、single、post-list、topなど | テンプレート部品をJSONで組み替えられる単位にする |
| `src/gutenberg/blocks/` | block.json中心の独自ブロック | AIエージェントが属性・innerBlocksを読んで生成しやすい |
| `build/` | 配布用CSS/JS | ソースと配布物を分離する |

## 設計原則として取り込むもの

| 原則 | 内容 | 理由 |
|---|---|---|
| 起動層を薄くする | `functions.php` は読み込みだけに寄せる | 変更事故を減らせる |
| 機能をfeature単位にする | `blocks`、`cta`、`affiliate`、`lp`、`tracking` のように分ける | 個人/法人で有効化を切り替えやすい |
| 設定を一元化する | PHP配列ではなくJSONマニフェストを正にする | AIエージェント操作と相性が良い |
| 表示部品を再利用化する | LPセクション、CTA、商品カード、FAQを部品化 | 記事/LP/トップで使い回せる |
| CSSを条件読み込みする | 使用ブロック・ページ種別ごとに読み込む | パフォーマンスに効く |
| 管理画面をパッケージ別に絞る | 個人は収益化、法人はLP/ブランド/CTA | 設定過多を避けられる |

## 参照テーマからの重要な学び

| 学び | 解釈 |
|---|---|
| 見た目より編集体験が重要 | 収益化やLP運用では、管理画面・ブロック・再利用部品が価値になる |
| ブロック設計が差別化になる | FAQ、Step、Review、Post List、Full Wideのような編集部品がコンテンツ品質を左右する |
| 設定量は制御が必要 | 多機能テーマは強いが、個人向けには設定過多になりやすい |
| REST/APIは慎重に作る | 計測や設定更新は便利だが、公開POSTは濫用対策が必要 |
| 法人向けは運用設計が価値 | 権限、再利用、ブランド統制、CTA計測、設定エクスポートが重要 |
