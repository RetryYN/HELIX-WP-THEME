# ADR-030: 計測ループは PULL(問い合わせ型/MCP風 read) を採用し PUSH を不採用

## Context

AGENT NEO の計測連携は、`tracking` イベントをどこで、どの権限境界で、どの方式で外部に渡すかが未確定だった。

- 従来の push/relay 方式では、backend 側の push 認証や本番 relay 運用の境界が重く、マルチテナント環境での認可設計の分離コストが高い。
- 一方、Automation SEO 側の再設計では、取得側を起点にする pull アーキテクチャへ移行しており、Theme/Core の read 契約を起点にする想定が前提になっている。

本 ADR は「計測は問い合わせ型で公開する」方向を採択する。

## Decision

- AGENT NEO は計測イベントを内部に蓄積（`agent_neo_tracking_event_queue`）し、`GET /agent-neo/v1/tracking/export` を公開して外部が pull する。
- `tracking/export` の read は `check_read_permission` 相当（ログイン + `edit_posts`）で保護し、既存接続権限で取得可能にする。
- Automation SEO 側はこの read 契約に合わせて再設計し、クエリ（`after / limit / event_type / since`）で逐次取得する。
- テナントは **Automation SEO 側接続情報で確定**し、AGENT NEO 側で push 先テナント認証を新規実装しない。
- レスポンス互換のため `schema_version` を返却し、互換性が必要な場合のみ version を更新する。

### 契約ポイント（要約）

- endpoint: `GET /agent-neo/v1/tracking/export`
- auth: read 接続と同等の `edit_posts` 権限ガード
- queryable: `after`, `limit`, `event_type`, `since`
- response: `schema_version, events[], next_cursor, count`

## Consequences

- backend の tenant-auth / 本番 relay 依存を排除し、AGENT NEO / Automation SEO の責務分離を明確化。
- Automation SEO は API 契約に合わせて pull 取得し、テナント確定や pull レート設計を管理側で実装。
- 今回の再設計（`tracking/export`）を起点に、今後の計測拡張（event_type 追加、metadata 追加）は `schema_version` で制御し、互換性を維持。

## Alternatives Considered

### PUSH + relay + backend 認証

- Automation 側からの push 受信を前提とし、AGENT NEO 側はイベント発火ごとに relay へ送信。

却下理由:

- 認証境界の実装負荷が高く、マルチテナント境界の設計が重くなる。
- 受信障害時の再送・遅延・監視実装が別途必要。
- 現在の計測再設計方針（Automation SEO が再設計）と整合しづらい。

### ハイブリッド（push + pull）

- push で即時連携しつつ、pull でも補完する。

却下理由:

- まず `tracking/export` を read 契約として明確化し、push の運用複雑さを先に増やすことを回避する。
- 一貫したテナント境界と監査設計が難しくなる。

### 本決定

**`GET /agent-neo/v1/tracking/export` を唯一の計測公開経路（read）として採用**。
