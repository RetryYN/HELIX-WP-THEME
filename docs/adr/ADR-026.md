## Context

### ブロックとしての位置づけ

`agent-neo/embed` は **Gutenberg のブロック挿入メニュー（block inserter）から、投稿（post）・固定ページ（page）・LP/HP 等、任意のブロック編集領域に差し込める標準的な Gutenberg ブロック**である。特定の post type に限定するものではなく、編集者が他のブロックと同じ操作感でブロックを 1 個挿入するだけで、AI 生成の自己完結 HTML（図解 / ゲーム / 診断）を表示できる。

dual-mode（iframe / Shadow DOM）は「テーマ CSS を引かない（テーマと相互非干渉）」を実現するための**内部実装の隔離手段**であり、編集者の挿入・表示操作には影響しない。投稿・固定ページ双方での利用を方針として明記する（block.json の `parent` 制約等の詳細は L4 carry）。

### AIが生成するフリーフォーム HTML の需要

Automation SEO は以下の「フリーフォーム自己完結 HTML」を生成するユースケースを持つ。これらは投稿・固定ページ等のコンテンツ領域のどちらにも差し込むことを想定している。

- **図解・インフォグラフィック**: SVG + HTML + CSS で構成された情報整理コンテンツ（テキストあり・SEO 対象）
- **簡単なゲーム**: JS を用いたインタラクティブなクイズ・チェックリスト（記事離脱低減・エンゲージメント目的）
- **診断系**: 入力フォーム + 結果表示（読者属性把握・サービス訴求）

これらは記事本文ブロックとは異なり、**HTML が自己完結**している（CSS・JS を内包、外部スタイルを必要としない）という特性を持つ。一方で、これらを記事ブロックとしてそのまま埋め込むと、テーマ CSS との相互干渉（テーマ CSS がブロック内部を崩す・逆にブロック CSS がテーマを汚染する）が発生するリスクがある。

### CSS 隔離要件

AGENT NEO のテーマ CSS と AI 生成 HTML は**相互非干渉**である必要がある。

- テーマ CSS はブロック内部のスタイルを上書きしない
- AI 生成 HTML の CSS・JS はテーマ・他ブロックのスタイル・DOM に漏洩しない
- 隔離を破るコードを Automation SEO 側が生成しても、テーマ側のレンダリング機構で封じ込める

## Decision

### ブロック名

`agent-neo/embed`（仮称。L4 実装時に block.json で確定）

### dual-mode 設計

Automation SEO が HTML を生成する時点でコンテンツ種別を判定し、**mode** を決定する。テーマ側はその mode に従って薄いレンダラとして動作する。

---

#### mode=interactive（ゲーム・診断系）

**対象コンテンツ**: ゲーム・診断・クイズなど JS 必須のインタラクティブコンテンツ（SEO インデックスを意図しない領域）。

**レンダリング機構**: **別オリジン sandboxed `<iframe src>`**

```html
<!-- テーマが出力するマークアップ（概念図 / 具体属性は L4 carry） -->
<iframe
  src="https://<sandbox-origin>/embed/{id}"
  sandbox="allow-scripts"
  title="[コンテンツ説明文 / a11y 必須]"
  loading="lazy"
  width="100%"
  style="border:none;"
></iframe>
```

> **sandbox-origin**: Automation SEO が生成・ホスト・配信する専用サブドメイン。テーマはこの URL を payload から受け取り、iframe の src にセットする薄いレンダラとして動作する。`<iframe srcdoc>` は廃止（→ Alternatives Considered「案D」参照）。

**セキュリティ設計原則**:

- sandbox 属性には **`allow-scripts` を含み、`allow-same-origin` を含まない**ことを不変条件とする。`allow-forms` 等の追加トークンは L4 設計判断として許容する（最終セットは CARRY-EMBED-002 で確定）。
  - `allow-same-origin` を付与すると iframe JS が親 DOM・Cookie・localStorage へアクセス可能になり、Automation SEO が生成した JS の XSS を封じ込められない。
  - `allow-same-origin` を外すことで親 DOM への `document.parent` アクセスを構造的に遮断する。
  - **`allow-top-navigation` / `allow-top-navigation-by-user-activation` も付与しない**（親ページへの強制遷移リスク排除）。
- `<script>` タグは sandbox 下（iframe 内）のみ許可。テーマ上位コンテキストでの `<script>` 実行は禁止。
- postMessage で高さ自動調整（iframe sizing）を行う。**sandbox 属性に `allow-same-origin` を含まないため、`<iframe src>` が別オリジン URL であっても iframe は opaque origin として動作し `event.origin` は `"null"` になる**。よって特定 origin 一致（`=== <sandbox-origin>`）の必須照合はできない。検証の主軸は **`event.source === iframe.contentWindow` の照合**（送信元 Window が自 iframe であることを確認）および**生成時にテーマが iframe に埋め込む一意トークン（nonce / payload-id）のペイロード内検証**の 2 点とする。`event.origin` の一致照合は必須要件としない（opaque origin 前提）。なお、cross-origin `<iframe src>` を採用した主目的は「**別オリジン文書として HTTP レスポンスヘッダに CSP を持ち、親ページの CSP を継承しない**（srcdoc 継承問題の解消）」であり、この CSP 分離の利点は origin が opaque であっても有効（CSP は HTTP レスポンスに付随して文書に適用される）。よって sandbox（`allow-same-origin` 不含）を維持しても CSP 隔離の設計意図は完全に保たれる。具体的な nonce 生成方式・メッセージスキーマは L4 carry（CARRY-EMBED-002）。
- `loading="lazy"` を付与し、ビューポート外では iframe を遅延ロードする。

**JS 許可根拠（REQ-F-036 是正後 / REQ-NF-001e 整合）**:

- **JS は「テーマ本体を重くしない」性能原則を守る範囲で許可**（REQ-F-036 (7) 是正後）。ゲーム・診断等インタラクティブコンテンツの JS は sandboxed iframe 隔離の条件下で許可される正規経路であり、「REQ-F-036 と矛盾」の状態を本判断で解消する。
- **非ブロッキング保証の文脈別定義（REQ-NF-001e との整合）**:
  - **ページ本体コンテキストの JS**（light DOM ブロック、親側 postMessage リスナー等）: REQ-NF-001e の `defer`/`async` 必須・メインスレッドブロック禁止・minify + tree-shake・1 ブロック ≤ 5KB 目安を引き続き適用する。
  - **mode=interactive の iframe 内 JS**: 別オリジン sandbox iframe（`src="https://<sandbox-origin>/embed/{id}"`）で配信されるため、inline `<script>` のコンテキストは sandbox-origin 文書内に完全に閉じている。`defer`/`async` 属性は外部スクリプト向けの仕様であり、sandbox-origin 文書内の inline `<script>` には適用しない。代わりに、`loading="lazy"`（ビューポート到達まで iframe 生成を遅延する）、page_type 性能予算へのカウント、**INP（Interaction to Next Paint）/ Long Task 実測（しきい値内であること）、および実行時間制限（CPU 負荷の高い処理は `requestIdleCallback` / Web Worker 化 / タイムアウト設定）**の組み合わせで非ブロッキング契約を担保する。**なお、sandboxed iframe は親ドキュメントと同一 renderer / メインスレッドを共有し得るため「別メインスレッドで動くから親をブロックしない」という保証は成立しない。**親ページの性能劣化が許容閾値内であることは、実測（INP / Long Task モニタリング）で検証する（具体しきい値・計測手法は CARRY-EMBED / PERF 系 carry で確定）。
- mode=interactive の AI 生成 JS は **別オリジン sandbox iframe 内に閉じ込め**（Automation SEO が sandbox-origin で生成・配信）、親（テーマ本体）コンテキストでは決して実行されない。これにより REQ-F-036 (1) の「ページ本体コンテキストでの inline `<script>` 禁止」と本 mode は排他でなく共存する。
- **埋め込みがあるページにのみロード**: interactive 埋め込みが存在するページに限り条件ロードされる最小の親側 postMessage リスナー（iframe 高さ更新のみ）を許可する（TC-068 / CARRY-EMBED-002）。iframe が存在しないページにはこのリスナーを一切ロードしない（= テーマ本体を重くしない / page-type アセット分離 L3-A4 §A と整合）。

**性能設計**:

- JS は interactive mode の iframe 内のみ（Automation SEO が sandbox-origin で生成・配信する AI 生成ロジック）。テーマ上位コンテキストでの **追加 JS は原則禁止**だが、**interactive 埋め込みが存在するページに限り、条件ロードされる最小の親側 postMessage リスナー（iframe 高さ更新のみ）を許可する**（TC-068 / CARRY-EMBED-002）。iframe が存在しないページにはこのリスナーを一切ロードしない。これにより REQ-NF-001a 予算原則は「不要なページにはロードしない」= L3-A4 §ページ別アセット分離で担保される。具体的なリスナー実装・メッセージスキーマ・`event.source === iframe.contentWindow` + nonce/payload-id の照合方式（`allow-same-origin` 不含のため `event.origin` は opaque / `"null"` になる前提で設計）は L4 carry（CARRY-EMBED-002）。
- **page-type 性能予算にカウント**（L3-A4 §ページ別アセット分離との整合）。interactive ブロックが存在するページは JS 予算を消費する扱いとし、CI の初期 JS 計測から除外しない。
- `prefers-reduced-motion` を iframe 内の CSS で尊重する旨を Automation SEO のサニタイズ仕様に含める（L4 carry）。

#### mode=static（図解・SVG/HTML+CSS）

**対象コンテンツ**: 図解・インフォグラフィック（SVG / HTML + CSS、テキストあり得る、JS なし or 最小限）。SEO インデックス対象。

**レンダリング機構**: **Shadow DOM（Declarative Shadow DOM / DSD）**

```html
<!-- テーマが出力するマークアップ（概念図 / 具体属性は L4 carry） -->
<div class="wp-block-agent-neo-embed" data-mode="static">
  <template shadowrootmode="open">
    <!-- Automation SEO が生成・サニタイズ済みの SVG/HTML+CSS -->
    <!-- <style> はここに閉じ込め、親スコープへ漏洩しない -->
  </template>
  <!-- light DOM フォールバック: JS/DSD 非対応ブラウザ向け（省略可。L4 で判断） -->
</div>
```

**設計原則**:

- **Declarative Shadow DOM（DSD）** を採用することで `innerHTML` JS 操作を必要とせず、SSR（サーバーサイドレンダリング / PHP render_callback）が可能。
- Shadow DOM の style は親スコープに漏洩しない（CSS encapsulation）。ただし **`font-family` / `color` / `line-height` / `font-size` 等の CSS 継承プロパティは shadow host を経由して既定で shadow 内要素に継承される**。Shadow DOM のカプセル化はセレクタベースのスタイルと非継承プロパティを遮断するが、継承プロパティは自動遮断されない。
- **テーマ継承スタイルからの完全な視覚隔離が必要な場合は、shadow root 内に明示的な host リセット（`:host { all: initial }` もしくは対象継承プロパティの明示リセット）を適用する**ことを設計要件とする。リセット適用範囲の具体化および例外（意図的に host からの継承を残す場合）は L4 carry（CARRY-EMBED-004 に含める）。
- テキストコンテンツは light DOM または shadowroot 内に含まれ、**可能な限り indexable** な状態を維持する。
  - 重要テキスト（見出し・説明文）は投稿・固定ページ等のコンテンツ領域の light DOM が担うことを原則とし、shadow root 内のテキストは補足に留める。
- JS は mode=static では不要（最小限の Intersection Observer のみ許容。L4 で判断）。

**SEO 設計**:

- mode=static は indexable 経路を維持することが設計意図。
- Googlebot は Declarative Shadow DOM を正しくレンダリングするため、シャドウ root 内のテキストは原則クロール対象となる（L4 で動作確認を TC に含める）。
- 重要なクロール対象テキスト（投稿・固定ページ等のコンテンツ領域に位置づけるべき情報）は、`agent-neo/embed` の外側のコンテンツブロック側に置くことを推奨する。

### 設計原則

#### 1. 生成・サニタイズ・mode 判定は Automation SEO 側

REQ-NF-025（AI ロジック完全分離）に従い、AI がどのコンテンツを生成し、どの mode を選択し、どのようにサニタイズするかの判断は **Automation SEO 側**が完全担当する。

テーマ（AGENT NEO）は検証済み payload の**薄いレンダラ**として動作する。テーマ側に AI 判断ロジック・コンテンツ生成ロジック・mode 判定ロジックは持たない。

> **セキュリティ sanitize は別扱い**: REQ-NF-025 が分離するのは「AI の判断・生成ロジック」であり、セキュリティ上のサニタイズ責務は対象外。Automation SEO 側の生成時 sanitize に加え、テーマ側も **defense-in-depth（多層防衛）として `wp_kses` / DOMPurify 等によるサニタイズを必須で保持する**（mode=static の Shadow DOM payload に適用）。mode=interactive では Automation SEO が sandbox-origin でコンテンツを完全ホストするため、テーマ側に untrusted JS payload が渡らない構造とする。テーマ側の mode=interactive defense-in-depth は **`frame-src` allowlist（sandbox-origin のみ）+ sandbox 属性不変条件**に集約する（具体 allowlist は CARRY-EMBED-004）。

#### 2. セキュリティ

- **iframe sandbox**: mode=interactive の AI 生成 JS は sandbox 内でのみ実行。不変条件: **`allow-scripts` を含む・`allow-same-origin` を含まない・`allow-top-navigation*` を含まない**。`allow-forms` 等の追加は L4 判断（CARRY-EMBED-002 で最終セット確定）。
- **CSP（Content Security Policy）**: 2層の CSP 構造を採用する（別オリジン sandbox iframe モデル）。
  - **サンドボックスオリジン CSP（sandbox-origin の HTTP レスポンスヘッダ）**: Automation SEO が sandbox-origin（`https://<sandbox-origin>/embed/{id}`）でホストする embed 文書は、**自身の HTTP レスポンスヘッダで CSP を配信**する。別オリジンであるため親ページの CSP を継承しない。`script-src` に自 origin のスクリプトのみを許可し、`connect-src` / `img-src` / `form-action` を `default-deny`（egress default-deny）とする。具体的なポリシー文字列は L4 carry（CARRY-EMBED-003）。
  - **親ページ CSP（HTTP ヘッダ）**: `script-src` / `default-src` 等を strict（`unsafe-inline` を含まない）に維持する。`frame-src` に **sandbox-origin のみを allowlist** する（例: `frame-src https://<sandbox-origin>`）。srcdoc-scoped CSP（`<meta>` prepend）は不要（別オリジン配信のため廃止）。具体 CSP 文字列は L4 carry（CARRY-EMBED-003）。
  - **親ページ CSP に `unsafe-inline` を全体付与してはならない**（sandbox-origin が別オリジンで自身の HTTP CSP を持つため、親側に inline 許可を追加する必要はない）。
- **【P1 / 残TL指摘 対応】egress 制御（CSP allowlist 必須）**: sandbox 属性に `allow-same-origin` を含まなくても、iframe 内 JS は `fetch` / `sendBeacon` / 画像リクエスト（`<img src>`）/ `navigator.sendBeacon` 等の**外部通信は止まらない**。診断フォームの入力値・選択肢が外部サーバへ exfiltration されるリスクがある。これを防ぐため、**CSP egress allowlist を必須**とする: `connect-src`・`img-src`・`form-action` を `default-deny`（`'none'` または 自 origin のみ）とし、iframe コンテンツが通信を必要とする場合は**明示的に許可 origin を列挙する**ことを要件とする。具体的な CSP 文字列・許可 origin リストは L4 carry（CARRY-EMBED-003 に追記）。本要件の検証 TC は TC-079（§10.1 末尾に追加）。
- **Automation SEO 側 allowlist sanitize**: Automation SEO が生成時に HTML タグ・属性の allowlist でサニタイズを実施する。テーマ側では defense-in-depth として `wp_kses` または DOMPurify 等での sanitize を必須で行う（直接 POST / 上流 sanitizer 漏れに備え、テーマ側でも入力を信頼しない。具体 allowlist は L4 carry（CARRY-EMBED-004））。
- **mode 別 sanitize 方針**（TC-072 と一致 / TC-067・TC-068 との矛盾を防ぐ）:
  - **mode=static（Shadow DOM / JS なし）**: テーマ側 sanitize（`wp_kses` / DOMPurify 等）で **`<script>` タグ・インラインイベントハンドラ（`onclick` 等）・`javascript:` URL を除去**する。JS は一切実行しない。
  - **mode=interactive（ゲーム / 診断 / 別オリジン sandbox iframe）**: テーマはコンテンツを直接保持せず、Automation SEO が sandbox-origin で生成・配信する。テーマ側の defense-in-depth は **`frame-src` allowlist（sandbox-origin のみ）+ sandbox 属性**（`allow-same-origin` 不含 / `allow-top-navigation*` 不含）に集約する。Automation SEO 側が生成時にサニタイズ・allowlist 検証を実施する（untrusted JS はテーマに持ち込まれない構造）。
- `<script>` タグは mode=interactive の別オリジン sandbox iframe 内（Automation SEO 配信）でのみ実行。mode=static の Shadow DOM 内では `<script>` を禁止する。

#### 3. 性能

- `loading="lazy"` で iframe を遅延ロード。
- JS は mode=interactive の iframe 内のみ（AI 生成ロジック）。テーマ JS バンドルへの追加は原則しない。ただし **interactive 埋め込みが存在するページに限り条件ロードされる最小の親側 postMessage リスナー（高さ更新のみ）を許可する**（§mode=interactive §性能設計 参照 / CARRY-EMBED-002）。
- **page-type 性能予算にカウント**（L3-A4 §ページ別アセット分離 / PERF-CARRY-007 との整合）。
- `prefers-reduced-motion` を尊重する（iframe 内の CSS / アニメーション制御を Automation SEO サニタイズ仕様に含める）。

#### 4. アクセシビリティ（基本配慮との整合）

- mode=interactive の iframe には `title` 属性を必須とする（基本 a11y 配慮 / L5 §5.1.A と整合）。
- キーボード操作：iframe 内コンテンツはキーボードでナビゲーション可能であること（Automation SEO サニタイズ仕様に含める）。
- 診断結果・フィードバックは `aria-live` 領域で出力（L5 §5.1.B / aria-live 設定チェックと整合）。
- mode=interactive でのアニメーションは `prefers-reduced-motion` を尊重する。

#### 5. SEO

- **mode=static**: indexable 経路を維持する。Declarative Shadow DOM 内テキストはクロール対象。
- **mode=interactive**: 設計上 非indexed（ゲーム・診断は SEO 的な価値コンテンツではなくエンゲージメントコンテンツ）。iframe sandbox 内コンテンツは Googlebot からクロールされない前提で設計する。
- 重要テキスト（キーワードを含む説明文など）は `agent-neo/embed` の外側（投稿・固定ページ等のコンテンツ領域の light DOM）が担う原則。

#### 6. WP 7.0 対応

- block.json に `apiVersion: 3` を使用する。
- **当ブロックは `supports.customCSS: false` を明示 opt-out** する（Shadow DOM / iframe で CSS 隔離が設計原則であるため、customCSS を有効化すると隔離が破壊される。ADR-020 D-4 / CARRY-WP7-004 の opt-out リストに最優先で追加）。
- Abilities API 宣言: readonly レンダリングのみを宣言する（`readonly: true`）。Automation SEO からの payload 受信は別の REST エンドポイント（`agent-neo/v1/posts/{id}/embed-block/apply`）で行い、Abilities 宣言と分離する（L4 carry / CARRY-EMBED-005）。

#### 7. 既存設計との整合

## Consequences

### 良い面

- **テーマ CSS と AI 生成 HTML の完全隔離**: 双方向の CSS 汚染リスクが構造的に解消される。
- **XSS 封じ込め**: mode=interactive の sandbox で AI 生成 JS が親 DOM・Cookie・storage に触れない。
- **SEO 経路の保護**: mode=static は indexable 経路を維持。mode=interactive は初めから非indexed として設計するため、SEO への悪影響が明示的に管理される。
- **ADR-004 整合**: ショートコードを使わずブロックとして実装するため、テーマ設計原則と完全整合する。

### 制約・トレードオフ

- **SEO 非indexed 領域が増える**: mode=interactive のゲーム・診断コンテンツは原則 Googlebot にクロールされない。重要な情報は投稿・固定ページ等のコンテンツ領域の light DOM に置く原則を徹底する必要がある。
- **iframe sizing / a11y コスト**: postMessage による高さ自動調整の実装・`title` 属性管理・`aria-live` 制御は Automation SEO 側の生成仕様に依存する。Automation SEO 側の実装品質が AGENT NEO 側のユーザー体験に直接影響する。
- **untrusted JS のサンドボックス必須**: `allow-same-origin` 禁止により iframe 内 JS がローカルストレージにアクセスできない。診断結果の永続化（ユーザーの入力保存）が制限される。**親 localStorage bridge は原則禁止**（`allow-same-origin` を外した隔離目的を守る。任意キー/任意値を read/write できる汎用 bridge を設けると sandbox 隔離が骨抜きになる）。永続化が本当に必要な場合でも、汎用 storage API 化は禁止とし、「namespace 固定 + 値 schema 検証 + write 専用（read 不可）」等の厳格プロトコルに限定する。**デフォルトは bridge を持たない方針を優先し、L4 carry に引き継ぐが「汎用 storage API 化は禁止」を不変制約とする**（CARRY-EMBED-002 に追記）。
- **Declarative Shadow DOM の SSR 詳細**: PHP の `render_callback` で DSD を出力する具体実装（template shadowrootmode 属性の PHP 生成）は L4 carry。
- **standalone / 個人版では mode=interactive は使用不可**: mode=interactive は sandbox-origin（Automation SEO が生成・ホスト・配信する専用サブドメイン）を必須とするため、Automation SEO との接続なしに単体テーマとして動作する standalone モードや個人版では mode=interactive は提供しない。これらの環境では mode=static（Shadow DOM）のみが有効な隔離モードとなる（CARRY-EMBED-004 に明示）。

## Alternatives Considered

### 案 A: scoped class prefix のみで CSS 分離

AI 生成 HTML に独自 class prefix（`ane-embed-xxx`）を付与し、テーマ CSS との衝突を名前空間で回避する案。

**却下理由**: AI 生成 HTML の CSS 規則がグローバルスコープに出力されるため、隔離は不完全。テーマの `*` セレクタ・要素セレクタ・継承プロパティ（`font-family` / `color` 等）がブロック内部に侵入するリスクを排除できない。Automation SEO が生成する CSS に prefix ルールを強制することも現実的でない。

### 案 B: 全コンテンツを iframe 化

mode=static の図解も iframe srcdoc で表示する案。

**却下理由**: 図解のテキストコンテンツが Googlebot にクロールされなくなり、SEO 上の損失が大きい。図解は情報価値の高いコンテンツであり、indexable 経路を切り捨てることは製品価値に反する。Shadow DOM（DSD）であれば SSR + SEO 維持が両立するため、図解には DSD を選択する。

### 案 C: テーマ側で HTML を生成する

AGENT NEO テーマが図解・ゲーム・診断 HTML のテンプレートを内蔵し、パラメータだけを Automation SEO から受け取る案。

**却下理由**: REQ-NF-025（AI ロジック完全分離）違反。テーマが生成ロジックを持つと「テーマ = 薄レンダラ」の原則が崩れる。また Automation SEO の生成内容の多様性に対応するためには、テーマ側に無数のテンプレートが必要になり保守コストが発散する。

### 案 D: `<iframe srcdoc>` による inline HTML 埋め込み（採用案Aに先行した検討案 / 却下済み）

Automation SEO が生成した自己完結 HTML を `srcdoc="..."` 属性にエンティティエスケープして埋め込む案。テーマが srcdoc 文字列を保持し render する。

**却下理由**:

1. **親 CSP 継承により inline JS 実行不可**: `srcdoc` iframe は親ページと**同一オリジン**（opaque origin だが親 CSP を継承）として扱われる。親ページが `script-src 'unsafe-inline'` を持たない strict CSP の場合、srcdoc 内の inline `<script>` は CSP 違反でブロックされる。mode=interactive のゲーム・診断コンテンツに不可欠な JS が実行できない。
2. **CSP 分離不可**: `srcdoc` iframe は親ページの CSP を継承するため、sandbox-origin が独自の HTTP レスポンスヘッダで CSP を配信するという分離構造を取れない。egress default-deny を実現するには srcdoc 内の `<meta http-equiv="Content-Security-Policy">` を全 untrusted payload より先に prepend する必要があり（理由④と連動）、HTTP ヘッダ配信と比べて信頼性が大幅に低下する。なお、`event.origin` については `srcdoc` + `allow-same-origin` なし でも採用案A（別オリジン `src` + `allow-same-origin` なし）でも、`allow-same-origin` を外した時点で iframe は opaque origin（`"null"`）になるため挙動は同じ。postMessage 検証は両者とも `event.source === iframe.contentWindow` + nonce に依拠する（§postMessage 設計原則参照）。
3. **srcdoc 属性コンテキストエスケープの実装負荷**: `srcdoc="..."` に代入する HTML は属性コンテキストのエンティティエスケープ（`"` → `&quot;`・`&` → `&amp;` 等）が必須であり、実装ミスによりサンドボックス適用前に親ドキュメントへのマークアップ注入が生じ得る。
4. **CSP meta 先頭 prepend の fragile 依存**: egress default-deny を実現するには srcdoc 内の `<meta http-equiv="Content-Security-Policy">` を全 untrusted payload より前に prepend する必要があり、実装順序に依存する脆弱な構造となる。

**採用案（案A）との対比**: 別オリジン sandbox iframe（`src="https://<sandbox-origin>/embed/{id}"`）では、sandbox-origin が独自の HTTP CSP ヘッダを配信するため①〜④の問題が構造的に解消される。親 CSP との干渉がなく、エスケープ問題がなく、CSP prepend 順序依存もない。なお `allow-same-origin` は案A でも付与しないため、`event.origin` は opaque（`"null"`）になる点は同じ。postMessage 検証は `event.source === iframe.contentWindow` + nonce が主軸（§postMessage 設計原則参照）。案A の利点は「HTTP レスポンスヘッダによる CSP の確実な分離・適用（srcdoc の meta prepend 依存を排除）」にある。
