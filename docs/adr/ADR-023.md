# ADR-023: クラシックテーマ資産の FSE 再設計コスト方針

- Status: Proposed
- Date: 2026-06-18
- Phase: L3 / Gate: G3
- 関連 GAP: GAP-RT-042（FSE 転換コスト）
- 参照 ADR: ADR-004（テーマ add_shortcode 禁止）/ ADR-005（SEO 統合 UX）/ ADR-019（Bridge Plugin 限定）
- 参照設計: L3-real-theme-gap-register.md GAP-RT-042 / §FSE 転換の構造的前提

---

## Context

### クラシックテーマ二極とFSE の構造的断絶

ThemeB 2.16.0 と テーマA 1.4.6 はどちらも**クラシックテーマ**（widgets + `functions.php` + customizer 中心の構成）である。AGENT NEO は**フルサイト編集（FSE / Block Theme）**で設計されており、WordPress のテーマアーキテクチャとして両者は別世代に属する。

実テーマ精読（解析レポート `18-テーマコーディングルール逆引き設計.md` / `32-ThemeB-asset-customizer-pipeline-deep-extract.md`）で確認されたクラシック固有の実装パターンは、FSE 上での直接移植が構造的に不可能な領域を多数含む。

### 各 addendum での「移植不可」判断一覧

A 群各 addendum が記録した「クラシック直接移植不可」判断を集約する。

| Addendum | クラシック資産 | FSE での直接移植可否 | 代替実装 |
|----------|---------------|---------------------|---------|
| A1（吹き出し） | `add_shortcode('fukidashi')` | **不可**（ADR-004 で確定済み） | `agent-neo/balloon` ブロック |
| A1（吹き出し） | `register_sidebar()` + ウィジェットエリア | **不可** | Block Template Part（サイドバー用） |
| A3（SEO） | `wp_head()` への直接 `echo`（sanitize_callback 欠落） | **不可**（XSS リスク） | `register_meta()` + `sanitize_callback` + `wp_kses` 準拠出力 |
| A3（SEO） | Customizer 経由の任意 head タグ挿入 | **不可**（Customizer は FSE で非推奨） | `wp_options` + 管理 REST API（`agent-neo/v1/settings/custom-tags`） |
| （横断） | `customizer` + `customize-selective-refresh-widgets` | **不可**（FSE は Customizer 非対応） | `theme.json` + Block Bindings API |
| （横断） | PHP テンプレートヒエラルキー（`single.php` / `archive.php` 等） | **不可**（FSE は block templates） | `templates/` ディレクトリ + HTML block template |

### L4 への波及

これらの「再設計必須」領域は L4 スプリントの構造に影響する。「移植」ではなく「再設計」であるため、対応スプリントのコスト見積もりが移植コストより高くなる。

---

## Decision

### 決定 1: クラシック資産の FSE 移行不可カテゴリと代替方針の確定

AGENT NEO は以下 4 カテゴリを「クラシック直接移植不可 / FSE 再設計必須」として正式に確定する。

---

**カテゴリ A: Customizer → theme.json + REST API**

| クラシック実装 | FSE 代替 | 根拠 |
|---------------|---------|------|
| `add_theme_support('customize-selective-refresh-widgets')` | 廃止・非採用 | FSE テーマは Customizer を使用しない |
| `get_theme_mod()` による色・フォント取得 | `theme.json` の `settings.color.palette` / `settings.typography` + CSS カスタムプロパティ | FSE 標準 |
| `add_theme_support('custom-background')` / `custom-header` | `theme.json` の `settings.background` / Block Template Header part | FSE 標準 |
| ThemeB `inc/customizer/font/`（Google Fonts 選択） | `theme.json` `settings.typography.fontFamilies` + Font Library API（WP 6.5+） | FSE 標準（GAP-RT-023） |
| ThemeB `inc/customizer/`（カラーテーマ全般） | `theme.json` `settings.color.palette`（AGENT NEO デザイントークン定義） | FSE 標準 |

**L4 への影響**: カラー / フォント / 背景はすべて `theme.json` 宣言で完結するため、PHP サイドに Customizer コードを書くスプリントは発生しない。ただし `theme.json` のデザイントークン設計スプリント（S-DESIGN-TOKEN）が独立して必要。

---

**カテゴリ B: PHP テンプレートヒエラルキー → Block Templates**

| クラシック実装 | FSE 代替 | 根拠 |
|---------------|---------|------|
| `single.php` / `single-{post_type}.php` | `templates/single.html` / `templates/single-{post_type}.html` | FSE block template |
| `archive.php` / `category.php` / `tag.php` | `templates/archive.html` / `templates/category.html` | FSE block template |
| `page.php` / `page-{slug}.php` | `templates/page.html` / `templates/page-{slug}.html` | FSE block template |
| `header.php` / `footer.php` | `parts/header.html` / `parts/footer.html`（Block Template Parts） | FSE template parts |
| `sidebar.php` + `register_sidebar()` + `dynamic_sidebar()` | `parts/sidebar.html`（Block Template Part）+ Query Loop / Latest Posts ブロック | FSE 標準 |
| `functions.php` のビジネスロジック | `functions.php` は bootstrap のみ（require で分割）。ロジックは `inc/` 配下のクラスに分離 | REQ-NF-011 / ADR-004 |
| `get_template_part()` によるパーツ読み込み | Block Patterns（`register_block_pattern()`）または Block Template Parts | FSE 標準 |

**L4 への影響**: テンプレート数 × 再設計コストが最大の実装負荷。個人版（HP / sidebar / archive / single の 4 テンプレート）は範囲が限定されるが、法人版（LP / BLP / HP + 複数サービス対応）は Blueprint システムと連動するため、L4 Phase A（BE Sprint）で Blueprint スキーマ確定後に L4 Phase B（FE Sprint）でテンプレート実装という順序制約が生じる。

---

**カテゴリ C: ウィジェット → Template Parts / Blocks**

| クラシック実装 | FSE 代替 | 根拠 |
|---------------|---------|------|
| `register_sidebar()` + `register_widget()` | Block Template Parts + 対応ブロック（Query Loop 等） | FSE 標準 |
| `dynamic_sidebar('sidebar-1')` | `<!-- wp:template-part {"slug":"sidebar"} /-->` | FSE 標準 |
| テーマA `inc/widget/` 配下のウィジェット群 | 対応ブロック or Block Pattern として再設計 | — |
| ThemeB `inc/widget/` 配下のウィジェット群 | 対応ブロック or Block Pattern として再設計 | — |

**L4 への影響**: ウィジェット系機能（人気記事・関連記事・SNS フィード等）は L4 スプリントで対応ブロックとして再設計する。ThemeB / テーマA のウィジェット実装を参考にしつつ FSE ブロックとして一から書くため、ウィジェット 1 種 = ブロック再設計 1 スプリントとして計上する。

---

**カテゴリ D: ショートコード → ブロック + 移行変換（ADR-004 の拡張確認）**

ADR-004「テーマ add_shortcode 禁止」で「テーマ側での `add_shortcode()` 呼び出しを禁止し、ブロック方式に統一する」と決定済み。本 ADR はその範囲を確認・拡張する。

| クラシック実装 | FSE 対応方針 | 移行変換 |
|---------------|------------|---------|
| テーマA `[fukidashi]` ショートコード | `agent-neo/balloon` ブロック（ADR-004 で確定済み） | Bridge Plugin が `[fukidashi]` → `<!-- wp:agent-neo/balloon -->` に変換（ADR-019 範囲） |
| テーマA `[jin_icon]` / `[icon_box]` | `agent-neo/icon-box` ブロック | 同上 |
| テーマA `[blogcard url=""]` | `agent-neo/blog-card` ブロック（GAP-RT-001 / L3-patch） | 同上 |
| 第三者プラグインのショートコード | AGENT NEO 側では変換しない。Bridge Plugin はショートコードを raw HTML として保持し、プラグインが引き続き処理する | — |

**AGENT NEO テーマ本体に `add_shortcode()` を書かない原則を本 ADR で改めて確認する。**

ショートコード互換レイヤー（既存コンテンツの `[fukidashi]` 等を WP 標準エディタで引き続き表示させる）は Companion Plugin（Bridge Plugin）の責務とし、テーマ本体は一切関与しない（GAP-RT-004 / ADR-019 整合）。

---

### 決定 2: 再設計コストの L4 織り込み

各カテゴリの再設計コストを L4 スプリント計画に以下のとおり織り込む。

| カテゴリ | 重いスプリント | コスト要因 |
|---------|--------------|----------|
| A: Customizer → theme.json | S-DESIGN-TOKEN（独立スプリント） | ThemeB / テーマA のカラー・フォント体系を AGENT NEO デザイントークン（CSS カスタムプロパティ + `theme.json`）に変換する設計作業 |
| B: PHP テンプレート → Block Templates | S-TEMPLATE-CORE（個人版 4 テンプレ）/ S-TEMPLATE-LEGAL（法人版 LP/BLP）| テンプレート 1 本 = ブロック再設計（HTML block template 記述 + PHP コアロジック分離）。法人版は Blueprint システムとの整合で追加コスト |
| C: ウィジェット → ブロック | S-BLOCK-WIDGET シリーズ | ウィジェット 1 種 = ブロック再設計 1 スプリント（block.json / edit.js / render.php / TC） |
| D: ショートコード → ブロック | S-BLOCK-CONTENT シリーズ（balloon / blog-card / icon-box 等） | ショートコード互換はテーマ対象外。ブロック実装のみ。Bridge Plugin 変換は ADR-019 スコープ |

**L4 Phase 構成への影響（確定事項）**:

- Phase A（BE Sprint）: Blueprint スキーマ確定 → テンプレート構造の基盤 REST 契約確定
- Phase B（FE Sprint）: Block Templates 実装（Phase A 完了後にのみ着手可能。依存関係あり）
- Phase A ∥ Phase B の並列化は Block Templates の構造スプリント（S-TEMPLATE-CORE）を除いた部分に限定する。

---

### 決定 3: テーマ本体への持ち込み禁止項目の確定

以下の実装パターンは AGENT NEO テーマ本体（`functions.php` / `inc/` 配下 / `templates/` / `parts/`）への実装を**禁止**する。

| 禁止パターン | 根拠 | 代替 |
|------------|------|------|
| `add_shortcode()` 呼び出し | ADR-004 / GAP-RT-004 | `agent-neo/*` ブロック |
| `register_sidebar()` / `register_widget()` | カテゴリ C / FSE 非推奨 | Block Template Parts |
| `add_theme_support('customize-*')` | カテゴリ A / FSE 非推奨 | theme.json |
| `get_theme_mod()` による色・フォント参照 | カテゴリ A | CSS カスタムプロパティ（theme.json 由来） |
| `wp_head()` への直接 `echo`（sanitize なし） | REQ-NF-002 / REQ-NF-011 | `wp_head` filter + sanitize_callback |
| PHP テンプレートヒエラルキー（`single.php` 等） | カテゴリ B / FSE Block Theme 原則 | `templates/*.html` |
| `session_start()` / PHP セッション管理 | ADR-004 / セキュリティ | WP transients / REST + JWT |
| jQuery 依存の JS | REQ-NF-001（jQuery dequeue 方針） | Vanilla JS / React（ブロック editor 側） |

## Consequences

### 良い面

- **L4 スプリント設計の明確化**: 再設計コストを「移植」と区別して計上するため、見積もり精度が向上する。
- **技術負債の予防**: クラシック資産を無理にコピーして FSE に持ち込むことで生じる「動いているが FSE 原則違反」コードを排除できる。
- **WordPress 標準への準拠**: Block Themes のベストプラクティス（`theme.json` / block templates / block patterns）に従うため、WP バージョンアップ耐性が高い。
- **ADR-004 整合**: テーマ `add_shortcode` 禁止とショートコード互換レイヤー（Bridge Plugin 担当）の責務分離が ADR-004 / ADR-019 と完全に整合する。

### 制約・リスク

- **L4 スプリント増大**: ウィジェット / テンプレート類の再設計は「移植」より工数が増える。特に ThemeB の Customizer カラー体系（解析レポート `32-ThemeB-asset-customizer-pipeline-deep-extract.md`）は独自実装が複雑で、デザイントークン変換スプリントのコストが高くなる可能性がある。

  → **対策**: S-DESIGN-TOKEN スプリントを L4 Phase A の最初に配置し、テーマ全体のデザイントークン基盤を先に確定してから各ブロック・テンプレートを実装する順序を工程表に明示する。

- **ユーザーの学習コスト**: ThemeB / テーマA からの移行ユーザーは Customizer に慣れており、`theme.json` + Site Editor（FSE）への移行で UI が変わる。

  → **対策**: ADR-019 の Bridge Plugin が移行ウィザード・Customizer 設定の `theme.json` 変換を担当する。テーマ本体は FSE 標準に従うのみ。

- **PHP テンプレートが存在しないことによる PHP 経由のクエリ制御不可**:
  クラシックテーマでは `archive.php` 内で `WP_Query` を直接書いてカスタマイズできたが、FSE では Block Template 内からの PHP クエリ制御は `render_callback` ブロックを介する。複雑な条件分岐（例: カテゴリ別に Sticky 記事を最上位に出す）はブロック側の `render_callback` に実装する必要があり、テンプレート自体はシンプルになるがブロック実装が増える。

  → **対策**: S-BLOCK-QUERY-LOOP スプリントで AGENT NEO 独自 Query Loop 拡張ブロックを実装し、カスタムクエリパラメータを block attributes で制御可能にする。

## 2026-06-20 追記: WP 7.0 GA 後の確定事実による補強

本セクションは 2026-06-20 時点の内部調査（`docs/research/wp-ecosystem-20260620.md`）に基づき、既存の決定を覆さず事実で補強する。

### theme.json v3 — 現行標準の確認

theme.json の **version 3 が現行標準**（WP 6.6+ / v4 予定なし）。AGENT NEO は新規開発のため v2 からの移行コストはゼロ。カテゴリ A（Customizer → theme.json）の設計方針を以下の確定事実で裏付ける。

| 機能 | 採用バージョン | AGENT NEO への適用 |
|---|---|---|
| `appearanceTools` | WP 6.2+ | 採用推奨（ブロック標準ツール群を一括有効化） |
| fluid typography（`clamp()`） | WP 6.1+ | 採用推奨（REQ-NF-001 性能予算・レスポンシブ対応） |
| 疑似クラス（`:hover` / `:focus` / `:focus-visible` / `:active`） | WP 7.0 | 採用（D-4 で確定済み） |
| dimension preset | WP 7.0 | 採用（D-4 で確定済み） |

（出典: `docs/research/wp-ecosystem-20260620.md` / developer.wordpress.org）

### Block Bindings API 段階確認（カテゴリ B 補強）

Block Bindings API は WP バージョン間で段階的に拡張されており、AGENT NEO が対象とする WP 6.6〜7.0 では以下が利用可能。

| WP バージョン | 追加された Bindings ソース | AGENT NEO での活用 |
|---|---|---|
| WP 6.5 | `core/post-meta`（初期対応） | 記事メタ / SEO 値をブロックに動的束縛 |
| WP 6.9 | `core/post-data`・`core/term-data` | タクソノミー・タームデータの束縛 |
| WP 7.0 | カスタムブロック対応 + pattern overrides | AGENT NEO 独自ソース登録・パターン単位の値上書き |

`register_block_bindings_source()` 実装時の必須要件: `current_user_can` による権限チェック・`show_in_rest: true`・`sanitize_callback`・transient キャッシュ。

これにより「テーマ = 計測 ID / メタ値の提供・ブロック束縛 / Automation SEO = AI 判断・生成データ」の責務分担（REQ-NF-025）と整合する。
※ 採否の正式凍結は ADR-027(D1/D2) を正本とする

### Interactivity API — Preact signals ベース確認（カテゴリ B 補強）

Interactivity API の変遷を確認し、AGENT NEO の「無駄 JS 禁止」原則（REQ-NF-001a）との整合を裏付ける。

| WP バージョン | 追加機能 |
|---|---|
| WP 6.5 | コア搭載（`@wordpress/interactivity`） |
| WP 6.6 | server directives 追加 |
| WP 6.7 | `subscribe()` 追加 |
| WP 7.0 | `watch()` 追加（現在 **Preact signals ベース**） |

**React 19 upgrade は互換問題で revert 中（WP 7.1+ 再挑戦予定）**。AGENT NEO は React / Vue を持たず Interactivity API（Preact signals）で軽量フロントを実現する方針であり、React 依存を持たないことで revert の影響を受けない。これは「独自 JS フレームワーク排除」の判断を補強する。

（出典: `docs/research/wp-ecosystem-20260620.md` / developer.wordpress.org/news）
※ 採否の正式凍結は ADR-027(D1/D2) を正本とする

### llms.txt — 低優先・見送り妥当 / AIクローラ向けは schema.org 主軸（ADR-022 cross-ref）

llms.txt は採用サイト約 10%・主要 AI ベンダーの本番 commit なし・Google 非対応明言のため、AGENT NEO の AI クローラビリティ設計（ADR-022 / REQ-NF-015）において**低優先とし見送りが妥当**。

AI クローラ向けのコンテンツ公開は **schema.org 構造化データを主軸**とする:
- マークアップ種別: `Article` / `BlogPosting` + `Author` + 日付（`datePublished` / `dateModified`）
- **content-parity 必須**: 構造化データに含まれるコンテンツとページ表示内容を一致させる（Google / AIクローラの評価基準）
- AIクローラ UA: GPTBot / ClaudeBot / Google-Extended は robots.txt を尊重。Grok / Perplexity は無視の報告あり（robots.txt だけでは制御できないケースに留意）

llms.txt 対応が必要と判断されるタイミングは「主要 AI ベンダー（Google / Anthropic / OpenAI）が本番 commit を公表した後」として L4 以降に先送りする。

（出典: `docs/research/wp-ecosystem-20260620.md` / 出典 URL: developer.wordpress.org/news の MCP Adapter 記事）

## Alternatives Considered

### 案 A: クラシック互換モード（Hybrid Theme）

FSE と Customizer の両方に対応するハイブリッドテーマにする案（`add_theme_support('widgets')` + Customizer + Block Templates を並存させる）。

**不採用理由**: WordPress はハイブリッドテーマを段階的に非推奨方向に進めており、WP 7.0 ではブロックテーマの位置づけが強化される（GAP-RT-027 / GAP-RT-030 参照）。今後の WP バージョンアップで Customizer 関連 API が削除・非推奨化された場合のメンテナンスコストが累積する。AGENT NEO は WP 6.6+ を対象とし、FSE に専念するほうが長期的に合理的。

### 案 B: テーマA のショートコードを AGENT NEO テーマで `add_shortcode` 互換として維持する

既存コンテンツのショートコード（`[fukidashi]` 等）を AGENT NEO テーマ本体で処理する案。

**不採用理由**: ADR-004 で明示的に禁止済み。テーマ GPL 公開時にショートコード互換レイヤーが含まれると将来の変更コストが増大し、AGENT NEO の拡張設計（ブロック方式）と競合する。Bridge Plugin による移行変換が正規経路。

### 案 C: 移植不可領域を「対応外」として L4 から除外する

ThemeB / テーマA の Customizer 体系やウィジェット群は「AGENT NEO 非対応」として機能提供しない案。

**不採用理由**: ユーザーが ThemeB / テーマA で使っていた機能（カラーカスタマイズ / サイドバーウィジェット / SNS フィード等）が AGENT NEO に移行後も利用できないと、テーマ乗り換えの意義が薄れる。再設計コストは増えるが、機能等価性の確保が製品価値に直結するため再設計を選択する。

## 2026-06-20 追記: theme.json v3 深掘り + create-block-theme 採用方針

> **出典**: `docs/research/wp-ecosystem-20260620.md` §theme.json v3 / §create-block-theme（公式ツール）  
> **スタンス**: 既存決定（カテゴリ A〜D）を変更しない。WP 7.0 GA（2026-05-20）後の確定事実で補強し、具体実装パターンを追記する。

### theme.json v3 — 採用詳細

ADR-023 §決定1 カテゴリ A では「Customizer → theme.json」への移行方針を確定したが、v3 固有機能の採用詳細は明記していなかった。WP 7.0 GA を受け以下を補強する。

| theme.json v3 機能 | WP バージョン | AGENT NEO 採用方針 | 移行コスト |
|---|---|---|---|
| `appearanceTools` | WP 6.2+ | **採用推奨**（ブロック標準ツール群を一括有効化。個別 `supports` 宣言を最小化） | ゼロ（新規開発） |
| fluid typography（`clamp()`） | WP 6.1+ | **採用推奨**（REQ-NF-001 性能予算・レスポンシブ対応。font-size を viewport 連動で最適化） | ゼロ（新規開発） |
| `:hover` / `:focus` / `:focus-visible` / `:active` 疑似クラス | WP 7.0 | **採用**（D-4 で確定済み。ボタン・CTA の状態設計を CSS 直書きから構造化） | ゼロ（WP 7.0 必須） |
| dimension preset（spacing / size） | WP 7.0 | **採用**（D-4 で確定済み。余白プリセットを構造化し AI 操作で名前指定可能に） | ゼロ（WP 7.0 必須） |

**WP 7.0 移行は慎重に（L4 注意点）**: `apiVersion` 3 の block.json を全ブロックに適用すると WP 6.6〜6.8 Tier A CI で互換チェックが必要になる。特に疑似クラスと dimension preset は WP 6.6〜6.8 環境でのフォールバック動作（無視されるだけか、エラーになるか）を L4 CI で確認すること（CARRY-WP7-004 参照）。

**v4 予定なし**: WP 7.0 時点で theme.json v4 の計画は公表されていない。v3 を長期 SSOT として設計できる。

### create-block-theme（公式ツール）— hybrid 2層採用方針

> **出典**: `docs/research/create-block-theme-investigation.md`

create-block-theme（Automattic 公式 GPL v2 プラグイン）は、デザイントークン層（color / typography / theme.json export）の流用に限定し、templates / patterns は独自実装とする **hybrid 2層方式** を採用する。

**採用スコープ（2層構造）**:

| 層 | create-block-theme の利用方法 | AGENT NEO の実装 |
|---|---|---|
| **Layer 1: design-token 層** | Style Book エディタで color palette / typography / spacing を設定し、`theme.json` として export → AGENT NEO テーマの `theme.json` 初期値生成に利用 | `theme.json` を正本として管理。create-block-theme export は初期値生成のみ（継続依存しない） |
| **Layer 2: templates / patterns** | **利用しない**（create-block-theme が生成する templates / patterns は参照テーマのデザイン意図を含み、ADR-010 「見た目コピー禁止」・ADR-004 に抵触するリスクがある） | 独自実装（`templates/*.html` / `register_block_pattern()`）|

**採用理由**:
- S-DESIGN-TOKEN スプリント（CARRY-ADR023-001）で Customizer 設定群を theme.json に変換する際、create-block-theme の Style Book エディタ + export ワークフローが初期値生成の参考 UI として有効
- templates / patterns は独自実装であるため GPL contamination リスクを切り離せる

**不採用範囲**:
- create-block-theme の templates / patterns export を AGENT NEO の templates / parts に取り込むことは禁止。ADR-010「見た目コピー禁止」・ADR-004 違反となる
- WP Playground との create-block-theme CI 統合（Playground + GitHub workflow）は参考情報として記録し、AGENT NEO CI（ADR-021）の設計時に考慮する

**具体パイプライン（L4 で確定）**: `create-block-theme export → theme.json 初期値生成 → AGENT NEO S-DESIGN-TOKEN スプリントで独自トークン体系に変換 → Ajv バリデーション（ADR-021）` のフローは L4 S-DESIGN-TOKEN Sprint 着手時に具体化する（CARRY-ADR023-001 blocking）。

## 2026-06-20 追記: テーマ構成方針（PO 指示 / 2026-06-20）

### 構成方針: ThemeB 主軸 + テーマA ハイブリッド

PO 指示（2026-06-20）: 「構成は ThemeB ベースで テーマA をハイブリッドする形式が理想」を受け、AGENT NEO のデザイン・機能・UX パリティの基準を以下のとおり確定する。

**ThemeB を主軸（base）とし、テーマA の強みをハイブリッドで接ぎ木する**設計方針を採用する。

#### 重要前提: FSE ネイティブ再実装（コードの fork ではない）

ThemeB / テーマA はいずれも**クラシックテーマ**であり、AGENT NEO は**FSE（ブロックテーマ）**として設計される（本 ADR §Context・§決定 1 参照）。

したがって「ThemeB ベース + テーマA ハイブリッド」とは、**クラシックコードの直接流用・fork を意味しない**。GPL v2 ライセンス上の問題と FSE / クラシックのアーキテクチャ世代差（Customizer / PHP テンプレートヒエラルキー / ウィジェット → theme.json / Block Templates / Block Patterns）により直接移植は技術的にも設計的にも不可である。

本方針は「ThemeB のデザイン・機能・UX をパリティ基準として AGENT NEO を FSE でネイティブ再実装し、テーマA の強みとして採点評価された機能・UX をハイブリッドで接ぎ木する」ことを意味する。

#### 根拠

- 解析レポート `27-AutomationSEO連携観点のThemeB-ThemeA採点`（Automation SEO 連携観点の採点比較）
- 解析レポート `41-運用サイト検証-ThemeA-ThemeB比較`（運用サイト検証での ThemeB / テーマA 比較）
- ブロックカタログ（L3-A1 addendum / 検証サイト実ブロック収録）
- 既存ビジョン「完全制御テーマ」（AGENT NEO テーマ戦略）

#### スコープと carry

どの機能を ThemeB 主軸とし、どの機能を テーマA からハイブリッドで採用するかの具体的なブロック対応表は、L4（block catalog 実装 Sprint）で確定する。L3 時点では方針と根拠のみを確定し、過剰な具体化は行わない。
