## Decision

### D-1: Abilities API — 採用（WP 7.0 GA 確認済み / 本格組み込みへ移行）

**判断: 本格採用（WP 7.0 GA 済みのため RC PoC フェーズは終了 → 本格組み込みへ移行）**

理由:

1. Abilities API（`wp_register_ability()`）は PHP API が WP 6.9 で導入（JS API は WP 7.0）された操作能力宣言機構であり、各ブロック・操作が `readonly` / `destructive` / `idempotent` / `requires_capability` を持つ設計に直結する。これは ADR-013 が定める「AI 側が安全に操作可否を判定できる製品契約」の機械実装として最適。
2. AGENT NEO の AI 操作契約（REQ-F-002 / REQ-F-003 / REQ-NF-015）は現行でも REST エンドポイント単位に操作注釈を持つ設計を意図しているが、WP 標準 API に乗ることで互換性・サードパーティ連携・WordPress.org 審査時の説明可能性が大幅に向上する。
3. 独自実装継続（`data-agent-*` DOM anchor のみ）よりも、WP 標準 API を基盤とした上に AGENT NEO 固有拡張を積む方が保守コストが低い。
4. WP 7.0 は 2026-05-20 に GA リリース済みであり、API シグネチャは確定している（RC 段階のリスクは解消）。

**採用方針:**

- **WP 7.0 GA 済みのため RC フェーズは終了**: Docker WP 7.0 環境で `wp_register_ability()` の実装と AGENT NEO ブロック登録との干渉を検証する（`tmp/wp7-compat/`）。RC PoC の確認義務は GA により本格組み込み検証に移行。
- **Full 組み込み**: WP 7.0 GA 確認済みのため、全ブロックの `block.json` に Abilities 宣言を組み込む（`agent-neo-abilities.schema.json` を L4 で策定）。
- **ADR-013 との整合**: ADR-013 の `data-agent-*` DOM anchor / snapshot / crawler access matrix は引き続き有効。Abilities API は「AI エージェントが操作可否を事前宣言する機構」として追加レイヤーに位置付ける。従来の REST エンドポイント注釈（`readonly` / `destructive` / `idempotent`）と Abilities API 宣言の二重管理を避けるため、**WP 6.9+ 環境では** Abilities API 宣言を SSOT とし、REST エンドポイントはそれを参照する設計とする。
- **WP 6.6〜6.8 向けバージョンガード設計（Tier A CI 必達 / P1 修正）**: Abilities PHP API（`wp_register_ability()` / `WP_Ability` クラス）は **WP 6.9 以降で導入** されており、Tier A CI 必達範囲（WP 6.6〜6.8）では利用できない。このため以下のバージョンガード設計を必須とする。

  **WP 6.9+ 環境**:
  - `wp_register_ability()` が利用可能。各ブロックに Abilities 宣言を組み込み、これを `readonly` / `destructive` / `idempotent` 等の操作注釈の SSOT とする。REST エンドポイント注釈はこれを参照する。

  **WP 6.6〜6.8 環境**:
  - PHP 側で `function_exists('wp_register_ability')` / `class_exists('WP_Ability')` によるバージョンガードを行い、Abilities API の呼び出しを条件付きで回避する（`wp_register_ability()` 不在による fatal error を防止）。
  - Abilities 未登録環境では、従来の **`data-agent-*` DOM anchor + REST エンドポイント注釈（`readonly` / `destructive` / `idempotent` フィールド）を独立した正規ソースとして機能させる**。REST 注釈は Abilities への参照を持たず standalone で SSOT として成立する設計とする。
  - これにより「Abilities 宣言を SSOT にする」という方針は **WP 6.9+ 限定**であり、WP 6.6〜6.8 では `data-agent-*` DOM anchor + REST エンドポイント注釈がその役割を担う。

  この設計により、WP 6.6〜6.8 環境でも fatal error ゼロ・REST 注釈の SSOT 参照欠落ゼロを保証し、Tier A CI の全セルで合格できる。
- **READ 公開 3 面の Abilities 経由公開（2026-06-20 追加）**: snapshot / crawl-map / llmo の READ 公開 3 面は、WP ネイティブ公開の実装機構として Abilities API（`permission_callback` + JSON Schema I/O など）を採用する方針とする。独自 REST エンドポイントのみで公開する案より将来の陳腐化リスクが低い。ただし**公開スコープ（認証要否 / allowlist / `meta.mcp.public` 等の具体値）は GAP-RT-052 の L4 entry 確定事項に従う**（現時点では断定しない）。MCP アダプター連携はローカル IPC 限定（ADR-024）を維持する。
- **write / 生成 / マーキング判断 = Automation SEO 完全集約 / WP Connectors 不採用（2026-06-20 追加）**: write 操作・AI 生成判断・マーキングロジックは Automation SEO 側に完全集約する（REQ-NF-025 AI ロジック完全分離原則）。WP 7.0 の Connectors API（OpenAI/Anthropic/Google 標準・multi-LLM）は**採用しない**。WP Connectors を採用すると AI ロジックがテーマ側に露出し、課金経路の崩壊と REQ-NF-025 / ADR-024 違反を招くため。

**様子見にしない理由（2026-06-20 更新）:** Abilities API の採用実態は 19 plugin / **0 theme**（2026-06-20 調査）であり、テーマ層での採用は業界横断でゼロ。AGENT NEO の先行採用は差別化として一層正当化される（出典: `docs/research/wp-ecosystem-20260620.md` / developer.wordpress.org/news のMCP Adapter 記事）。

### D-3: リアルタイム共同編集 — セッション非依存設計を堅持し、競合検証 TC を追加

**判断: AGENT NEO はセッション非依存設計を基本とし、共同編集との競合を L4 検証 TC で必達確認**

WP 7.0 の共同編集（Collaborative Editing）は HTTP polling + presence + postmeta/transient 周辺の同時書き込みを前提とする。AGENT NEO の REST 操作が共同編集セッション中の記事を書き換えた場合の衝突リスクが GAP-RT-028 として指摘されている。

**基本方針:**

1. **セッション非依存設計の維持**: AGENT NEO 側の REST 操作はセッション状態に依存しない。`session_start()` / `session_status()` をテーマ本体に持たない（テーマA は 4 件存在するが AGENT NEO は 0 を維持）。
2. **書き込み操作は明示 API 経由に限定**: postmeta 直接更新 / AJAX 書き込みはテーマ本体には持たず、agent-neo/v1 REST エンドポイントに集約する（REQ-F-021 / REQ-F-022 の partial update・section edit 経路が正規経路）。
3. **衝突検出の仕組み**: AGENT NEO の REST 操作（PATCH /agent-neo/v1/posts/{id}/blocks/{block_id}）は `If-Match: <revision_hash>` ヘッダを受け付け、編集者のリビジョンと一致しない場合に `409 Conflict` を返す。共同編集者が同時編集中の場合は WP の `_edit_lock` / `_edit_last` postmeta を確認し、lock 中は AGENT NEO REST 操作を `423 Locked` で拒否（強制上書き禁止）。
4. **Automation SEO 側への責務分離**: 衝突が発生した場合の「どちらの変更を優先するか」の判断ロジックは Automation SEO 側に委任する（REQ-NF-025 AI ロジック完全分離原則）。AGENT NEO 側は競合検出 + エラーレスポンス + dryRun 提供のみ。

**共同編集 OFF 時の保証**: 共同編集が OFF の環境では現行 REST 操作と挙動は変わらない。AGENT NEO の Tier A CI マトリクスでは共同編集 ON/OFF 両方を検証セルに含める。

### D-4: theme.json / block 新機能 — 積極 adopt を基本とし、customCSS は精査 opt-out リストを管理

**判断: WP 7.0 の theme.json 拡張を積極 adopt とし、customCSS 自動有効化はブロック単位で精査**

WP 7.0 で導入される theme.json / block 系新機能への方針を以下の 3 分類で整理する。

**Adopt（積極採用）:**

| 機能 | 方針 | 理由 |
|---|---|---|
| 疑似クラス（`:hover` / `:focus` / `:focus-visible` / `:active`）| theme.json に移行 | ボタン・CTA・カードの状態設計を CSS 直書きから構造化できる。AI 操作時の hover 状態を JSON で制御可能になる |
| dimension preset | theme.json に定義 | 余白・横幅・高さプリセットを構造化し、AI 操作でプリセット名を指定できる。個別 CSS 指定を排除してバイト削減 |
| navigation-overlay template part | theme.json で登録 | FSE モバイルナビ設計を WP 標準に寄せる。テーマ独自 JS ナビを不要にしてバイト削減（REQ-NF-001a JS 予算に直結） |
| DataViews / DataForm | 管理画面 UI に採用候補 | AGENT NEO 管理画面・Automation SEO 連携 UI を WP 標準寄りに寄せることで保守コスト削減 |

**Opt-out 精査（ブロック単位で管理）:**

| 機能 | 方針 | 理由 |
|---|---|---|
| `supports.customCSS` 自動有効化 | 全ブロックの block.json を点検し、outer wrapper が不安定なブロックは `"customCSS": false` で明示 opt-out | WP 7.0 でブロック単位の CSS 指定が自動有効化されると、サーバーサイドレンダリングブロック・独自 CSS を持つブロックで outer wrapper 崩れが起きうる。GAP-RT-027 記載リスク |

opt-out リストは `docs/wp7-compat/block-custom-css-optout.md` として L4 で管理する。

> **⚠️ WP 7.0 起因 要警戒事項: `supports.customCSS` 自動有効化（2026-06-20 重要度 elevate）**
>
> WP 7.0 の `supports.customCSS` 自動有効化は、AGENT NEO の**全ブロック**に対して影響する横断リスクである。特にサーバーサイドレンダリングブロック（`render_callback` を持つブロック）・独自の `innerHTML` 操作を行うブロック・Interactivity API `data-wp-*` 属性を使うブロックでは、 `customCSS` 経由でユーザーが任意のセレクタを追記した場合に outer wrapper 崩れ・スタイル干渉・インタラクション破壊が起きうる。  
>
> **対応方針（L4 必須）**: CARRY-WP7-004 に従い、L4 ブロック実装時に **全ブロックの block.json に `"customCSS": false` が必要かどうかを checklist 項目として確認** し、opt-out リスト（`docs/wp7-compat/block-custom-css-optout.md`）を整備する。特に以下は opt-out 候補として最優先で点検すること:
> - `agent-neo/embed`（ADR-026: Shadow DOM / iframe 隔離ブロック / CSS 隔離が設計原則のため `customCSS` は設計上不要・有効化は隔離破壊に直結）
> - `agent-neo/hero` / `agent-neo/cta`（outer wrapper に position:relative + z-index 制御があるもの）
> - Interactivity API `data-wp-*` を使う全ブロック（セレクタ競合がディレクティブを壊す可能性）
>
> TC-WP7-012（opt-out リスト記載ブロックで `customCSS=false` が確認でき outer wrapper が崩れないこと）は P1 / CI 必達。

**様子見（WP 7.0 final 確認後に判断）:**

| 機能 | 様子見理由 |
|---|---|
| DataViews / DataForm の深い統合 | API が RC 段階では不安定。final 後に安定 API を確認して本実装判断 |

## 2026-06-20 追記: WP 7.0 GA 後の事実反映

本セクションは 2026-06-20 時点の内部調査（`docs/research/wp-ecosystem-20260620.md` / Haiku 4体並列）に基づき、WP 7.0 が GA（2026-05-20）となった後の確定事実を反映するものである。既存決定（D-1〜D-4）は**変更しない**。

### WP 7.0 AI インフラ 4 本柱（確定）

WP 7.0 は以下の 4 本柱を標準装備として出荷した（「エンドユーザー AI 機能」ではなく「AI インフラ」であり、機能は plugin 側が乗せる前提）。

| 機能 | 概要 | AGENT NEO との関係 |
|---|---|---|
| **Connectors API** | OpenAI / Anthropic / Google 標準の multi-LLM 接続 API | **採用しない**（AI ロジック露出・課金経路崩壊リスク。REQ-NF-025 / ADR-024） |
| **Abilities API** | PHP=WP6.9・JS=WP7.0。操作能力宣言機構（`wp_register_ability()`） | **採用する**（D-1 で確定。GA により RC PoC から本格組み込みへ移行） |
| **PHP AI Client SDK** | LLM 呼び出しの PHP 標準ライブラリ | **採用しない**（AI 呼び出しは Automation SEO 側が完全担当） |
| **MCP Adapter** | Abilities → MCP → Claude/Cursor/VSCode 接続（公式） | **ローカル IPC 限定で参照**（ADR-024 維持。MCP はサーバー公開しない） |

### Abilities API 採用実態（2026-06-20 調査）

- 採用: **19 plugin / 0 theme / 約 8 割 read-only**（業界全体でテーマ採用ゼロ）
- AGENT NEO の Abilities API 採用は「テーマ層初の採用事例」となる見込みであり、D-1 で示した差別化論拠をさらに強化する

### WP 7.1 AI Guidelines — 監視対象

WP 7.1（2026-08-19 予定）で **AI Guidelines feature**（editorial rules の import/export）が追加される予定（出典: make.wordpress.org/core/2026/06/19/roadmap-to-7-1/）。AGENT NEO のスタイルガイド構想と重複・競合の可能性がある。仕様公開後に設計整合を確認する（PO-WP7-05 参照）。

## 2026-06-21 追記: CARRY-WP7-001 Abilities API 実測結果

CARRY-WP7-001（Abilities API 本格組み込み検証）は **VERIFIED（2026-06-21）**。WordPress 7.0 (GA) と WordPress 6.9.4 の双方で、検証用 mu-plugin `poc/wp7-abilities/zz-abilities-verify.php` による `agent-neo` category 登録、`agent-neo/diag-ping` ability 登録、`wp_get_ability()` 取得、`execute` 実行までを確認した。実行結果は `{"pong":true,"echo":"neo7"}`、登録戻り値は `OK:WP_Ability`、`total_abilities=4`（core 3 + 自前 1）。詳細証跡は `poc/wp7-abilities/RESULTS.md` を正本とする。

登録契約として、Abilities API は WP コア 6.9.0+ 標準（`wp-includes/abilities-api.php`）であり、登録は `wp_abilities_api_categories_init` で category を作成してから `wp_abilities_api_init` で ability を登録する二段構成が必須。category は `label` と `description` の両方を持つ必要があり、ability の `category` は登録済み category でなければならない（未登録 category を指定した register は `null`）。

## Consequences

**良い面:**

- WP 7.0 対応を設計に明示することで商用テーマとして「WP バージョン追随保証」を訴求できる。
- Abilities API 採用で ADR-013（AI 運用性製品契約）が WP 標準基盤と整合し、AI エージェント連携の説明可能性が高まる。
- 互換 CI マトリクスにより WP/PHP 更新時の回帰を自動検出でき、REQ-NF-013 の運用品質要件を CI で担保できる。
- セッション非依存設計の堅持により、共同編集環境での AGENT NEO 操作が予測可能になる。
- theme.json 拡張積極採用で JS/CSS バイト削減（REQ-NF-001a / REQ-NF-001f 性能予算）に直結。

**制約・リスク:**

- ~~Abilities API の RC → final 間での API シグネチャ変更リスクがある。PoC 投資が無駄になる可能性を受け入れた上で先行採用を選択する。~~ → **GA 済み（2026-05-20）により API シグネチャは確定。RC 乖離リスクは解消済み。**
- CI マトリクスが 5 WP × 4 PHP = **20 セル**になるため、CI 実行時間が増加する。並列化で吸収する。（WP 7.0 は GA 済みのため Tier B RC レーンは不要となり、当初想定の「RC 2 セル」は Tier A 必達マトリクスへ統合済み / CARRY-WP7-012）
- **WP 6.6〜6.8 では Abilities PHP API（`wp_register_ability()`）が不在**。バージョンガード（`function_exists` / `class_exists`）実装が L4 必須事項であり、未実装の場合 Tier A CI（WP 6.6〜6.8 セル）が fatal error で FAIL する。`data-agent-*` DOM anchor + REST エンドポイント注釈が 6.6〜6.8 での standalone SSOT として確実に機能するよう設計・検証すること（TC-WP7-014 参照）。
- customCSS opt-out 管理リストはブロック追加時に更新が必要。ブロック追加時の checklist 項目に加える。
- 共同編集環境での `423 Locked` 拒否は AI 操作の失敗率を高める。Automation SEO 側でリトライロジックを実装する必要がある（AGENT NEO 側の責務外）。

## Alternatives Considered

### A-1: Abilities API を様子見する（独自 DOM anchor 継続）

`data-agent-*` DOM anchor と REST エンドポイント注釈のみで継続する案。

却下理由: ThemeB / テーマA が 0 実装のうちに先行採用することが差別化になる。ADR-013 の製品契約としての訴求力が低下する。WP 標準 API 不採用で WordPress.org 審査時の説明コストが増す。

### A-2: PHP 8.1 以下を全てサポート対象とする

PHP 7.4 / 8.0 を CI 必達対象に含める案。

却下理由: PHP 7.4 は PHP 公式 EOL 済み（2022-11-28）。ホスティング互換として情報提供は行うが、セキュリティ問題を持つ PHP バージョンを必達対象にすることは商用テーマとして適切でない。PHP 8.1 が現行 LTS のため、8.1 を下限とした。

### A-3: 共同編集との衝突を WP 側に完全委任する（AGENT NEO は対処しない）

WP コアの共同編集が衝突処理するため AGENT NEO 側で何もしない案。

却下理由: AGENT NEO の REST 操作は WP 標準エディタと異なるセッション外のパス（cron / Automation SEO 連携）から実行される場合があり、WP コアの共同編集 UI ではカバーされない。`_edit_lock` 確認と `423 Locked` 拒否を AGENT NEO 側で実装しないと、編集者の保存が AI 操作で上書きされるリスクが残る。

### A-4: theme.json 拡張を全て様子見する

WP 7.0 final まで全機能を見送る案。

却下理由: 疑似クラス / dimension preset / navigation-overlay は JS 削減（REQ-NF-001a）と直結する機能であり、先行採用の恩恵が大きい。final リリース前に PoC で確認する時間的余裕がある。
