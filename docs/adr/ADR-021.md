# ADR-021: OSS / CI toolchain 選定（PHP互換・型解析・スキーマ検証・供給チェーン）

- Status: Proposed
- Date: 2026-06-18
- Phase: L3 / Gate: G3
- 解決 GAP: GAP-RT-029, GAP-RT-031, GAP-RT-032, GAP-RT-033, GAP-RT-034, GAP-RT-035
- 関連 TC: TC-016（a11y gate）, TC-027（SBOM gate）, TC-028（Lighthouse CI render-blocking）
- 関連要件: REQ-NF-005（a11y）, REQ-NF-011（テーマコーディング規約）, REQ-NF-013（運用品質）, REQ-NF-016（配布準備）, ACC-NF-005, ACC-NF-010

---

## Context

AGENT-NEO は PHP 8.1+ を前提とした WordPress FSE テーマである（REQ-F-001）。
監査（`L3-real-theme-gap-register.md`）で以下 5 件の GAP が「B OSS/CI ツールチェーン」カテゴリで OPEN のまま残存していた。

| GAP-ID | 内容 |
|---|---|
| GAP-RT-029 | PHP 8.2〜8.5 互換マトリクスの CI テストが未設計 |
| GAP-RT-031 | PHPCompatibilityWP の ADR 記載なし |
| GAP-RT-032 | PHPStan の level 設定・baseline が ADR 未記載 |
| GAP-RT-033 | `opis/json-schema` の採用可否が ADR 未記載 |
| GAP-RT-034 | Ajv のバージョン・strict モード設定が ADR 未記載 |
| GAP-RT-035 | `composer audit` の CI 組み込みと fail 基準が ADR 未記載 |

加えて、解析レポート `40-OSSライブラリ技術転用候補.md` に一次整理された「すぐ採用する技術セット（P0）」の中で、テーマコーディング規約（REQ-NF-011）・運用品質（REQ-NF-013）・配布準備（REQ-NF-016）・SBOM 生成（TC-027）・Critical CSS 抽出（GAP-RT-021 の PERF-CARRY-001）について設計記録が存在しなかった。

本 ADR はこれらを一括して意思決定を記録し、L4 CI 設計の正本とする。

---

## Decision

### 採用区分定義

| 区分 | 意味 |
|---|---|
| **P0 必須** | L4 実装前に CI に組み込み、gate 通過条件とする |
| **P1 推奨** | L4 で組み込み、未達は carry とするが CI fail は任意 |
| **PoC 保留** | L4 で評価し、L5/L6 で採否確定する |

---

### 決定一覧

#### A. PHP バージョン互換（GAP-RT-029 / GAP-RT-031）

**P0 採用: PHPCompatibilityWP**

- ツール: `phpcompatibility/phpcompatibility-wp`（Composer dev 依存）
- 対象バージョン: PHP 8.1 〜 8.4（testVersion = `8.1-8.4`）
- 根拠: AGENT-NEO は「PHP 8.1+」を宣言（REQ-F-001）しており、8.2 以降の deprecated dynamic properties / 型強化で WordPress API 呼び出しが壊れうる（GAP-RT-029）
- CI 配置: PR マージ前（静的解析フェーズ）＋週次 scheduled run（PHP 8.5 RC 対応のため）
- ライセンス: LGPL-3.0（Composer dev 依存のみ、配布物に含まない）
- 代替: `exakat/php-static-analysis`（重量級・却下）、phparkitect（アーキテクチャルールに特化・別用途）
- fail 基準: ERROR 件数 > 0 → CI fail

```bash
# composer.json への追加
composer require --dev phpcompatibility/phpcompatibility-wp:^2.1

# phpcs.xml.dist 設定
<rule ref="PHPCompatibilityWP"/>
<config name="testVersion" value="8.1-8.4"/>

# 実行コマンド
vendor/bin/phpcs --standard=phpcs.xml.dist --runtime-set testVersion 8.1-8.4 .
```

#### B. PHP 静的型解析（GAP-RT-032）

**P0 採用: PHPStan + szepeviktor/phpstan-wordpress + phpstan-wordpress-stubs**

| ツール | Composer パッケージ | 役割 |
|---|---|---|
| PHPStan 本体 | `phpstan/phpstan:^1.11` | 型・未定義・到達不能コード検出 |
| WP 型補完 | `szepeviktor/phpstan-wordpress:^0.7` | WordPress グローバル関数・フックの型定義 |
| WP スタブ | `php-stubs/wordpress-stubs:^6.6` | WP コア・プラグイン API の phpstan 用スタブ |

- 採用 level: **level 5**（未定義変数・型不整合・戻り値型を検出）
  - level 8 / 9 は WP プラグイン + スタブ互換性が未成熟なため L4 着手時は 5 から開始
  - L4 完了後 level 6 への段階引き上げを CARRY-ADR-021-001 に記録（後述）
- baseline: 初回実行時に `phpstan.baseline.neon` を生成し、既存 WARNING を baseline 化。新規コードは baseline 未収録の error を 0 に保つ
- ライセンス: MIT（全 3 ツール）
- 代替: Psalm（PSR-13 完全互換だが WP スタブが弱い）→ PoC 保留
- CI 配置: PR マージ前（静的解析フェーズ）
- fail 基準: baseline 差分の ERROR > 0 → CI fail

```bash
composer require --dev phpstan/phpstan:^1.11 \
  szepeviktor/phpstan-wordpress:^0.7 \
  php-stubs/wordpress-stubs:^6.6

# phpstan.neon.dist
parameters:
  level: 5
  paths:
    - src/
    - includes/
  bootstrapFiles:
    - vendor/php-stubs/wordpress-stubs/wordpress-stubs.php
```

#### C. JSON Schema 検証（GAP-RT-033 / GAP-RT-034）

AGENT-NEO は設計上 JSON 契約を多数持つ（`seo-profile.schema.json` / `seo-meta.schema.json` / `entity-graph.schema.json` / `seo-conflict-rules.schema.json` / `critical-css.schema.json` 等）。PHP 側・JS ビルド側の両方でスキーマ検証を行う。

**C-1. P0 採用（PHP 側）: opis/json-schema**

- パッケージ: `opis/json-schema:^2.3`
- JSON Schema 仕様: Draft 7 / Draft 2019-09 対応
- 用途: Core Plugin の REST ハンドラ内でリクエスト body を `schema.json` に対して検証し、invalid 時は `422 VALIDATION_ERROR` を返す
- テーマ本体（表示層）には組み込まない（REQ-NF-008 の「Theme Core は FSE 表示層に限定」原則に準拠、Core Plugin 配置）
- ライセンス: Apache-2.0
- 代替: `justinrainbow/json-schema`（メンテナンス頻度が低い）、`league/json-guard`（Draft 4 止まり）→ 不採用
- CI 配置: Unit テスト層（PHPUnit でスキーマ検証ロジックをカバー、主要スキーマ 100%）

```bash
composer require opis/json-schema:^2.3

# 使用例（Core Plugin 内）
use Opis\JsonSchema\Validator;
$validator = new Validator();
$result = $validator->validate($data, $schema);
if (!$result->isValid()) {
    return new WP_REST_Response(['code' => 'VALIDATION_ERROR'], 422);
}
```

**C-2. P0 採用（JS 側）: Ajv v8（ajv@^8）**

- パッケージ: `ajv@^8.17`（npm dev dependency）
- バージョン選定理由: Ajv v8 は JSON Schema Draft 2019-09 / Draft 2020-12 対応、`strict` モードをデフォルト有効化し、未知の keyword を含む schema を error とする
- 設定:
  - `strict: true`（デフォルト維持）
  - `allErrors: true`（全エラーを収集してから返す）
  - `coerceTypes: false`（型の自動強制を禁止）
- 用途:
  - `@wordpress/scripts` の webpack/esbuild ビルドパイプライン内で schema.json のコンパイル時検証
  - 管理画面 React コンポーネントの props validation（`block.json` の `attributes` 検証）
  - Node.js CI スクリプト内での JSON 生成物の検証
- ライセンス: MIT
- 代替: Ajv v6（Draft 7 のみ、メンテナンス縮小）→ 不採用。zod（TS-first だが JSON Schema 出力に追加変換が必要）→ PoC 保留
- CI 配置: `@wordpress/scripts` ビルドフェーズ（PR マージ前）

```bash
npm install --save-dev ajv@^8.17 ajv-formats@^3.0

# validate.mjs（CI スクリプト例）
import Ajv from 'ajv';
import addFormats from 'ajv-formats';
const ajv = new Ajv({ strict: true, allErrors: true });
addFormats(ajv);
const validate = ajv.compile(schema);
if (!validate(data)) {
  console.error(validate.errors);
  process.exit(1);
}
```

#### D. 供給チェーン脆弱性スキャン（GAP-RT-035）

**P0 採用: composer audit**

- バージョン: Composer 2.5+ 組み込み（追加パッケージ不要）
- fail 基準: **severity = critical または high の脆弱性が 1 件でも存在 → CI fail**（medium 以下は report のみ）
- CI 配置: PR マージ前（セキュリティフェーズ）＋週次 scheduled run
- ライセンス: MIT（Composer 本体）
- 代替: security-checker（2022 年 EOL・不採用）、Snyk CLI（SaaS 依存・PoC 保留）

```bash
# fail on critical/high のみ。medium/low は警告ログのみでジョブは pass（report-only）。
#
# [背景] set -o pipefail 有効下では `composer audit` が medium/low を含む任意の advisory で
# 非0終了する。パイプで jq に渡すと audit の非0終了が先に伝播し、severity フィルタが
# 効く前にジョブが落ちる。そのため audit の exit code を中和してから JSON を評価する。
#
# .advisories の実形状: { "vendor/package": [ {severity, title, ...}, ... ], ... }
# .advisories[][] で「パッケージ→advisory オブジェクト」の 2 段展開で全件を平坦化する。

# 1. JSON をファイルへ書き出す（audit 非0終了は中和。脆弱性なしの場合も 0 バイトになりうる）
composer audit --format=json > audit.json || true

# 2. 空ファイル検出（audit 自体が実行失敗した場合 → fail）
test -s audit.json || { echo "ERROR: audit.json が空です（composer audit が実行失敗した可能性があります）"; exit 1; }

# 3. JSON 妥当性確認（.advisories キーが存在しない形式 → fail）
jq -e 'has("advisories")' audit.json > /dev/null || { echo "ERROR: audit.json に .advisories キーがありません"; exit 1; }

# 4. medium/low を report-only で出力（情報のみ、ジョブは継続）
LOW_COUNT=$(jq '[.advisories[][] | select(.severity == "medium" or .severity == "low")] | length' audit.json)
if [ "$LOW_COUNT" -gt 0 ]; then
  echo "WARN: medium/low advisory が ${LOW_COUNT} 件あります（report-only、ジョブは pass）"
  jq '[.advisories[][] | select(.severity == "medium" or .severity == "low") | {severity, title, link}]' audit.json
fi

# 5. critical/high が 1 件でも存在すれば fail
jq -e '[.advisories[][] | select(.severity == "high" or .severity == "critical")] | length == 0' audit.json
```

**P1 推奨: CycloneDX PHP Composer（SBOM 生成）**

- パッケージ: `cyclonedx/cyclonedx-php-composer:^5.1`（dev 依存）
- 仕様: CycloneDX 1.4（XML / JSON 両形式）
- 用途: TC-027（SBOM gate）の達成。release build 時に `sbom.cdx.json` を生成し、Theme Review 提出前に artifact として確定させる
- CI 配置: release ブランチビルド時のみ（PR では optional）
- ライセンス: Apache-2.0
- fail 基準: release build で `sbom.cdx.json` が生成されていない場合 CI fail（TC-027 受入条件）

**PoC 保留: Trivy filesystem scan**

- 用途: コンテナ・ファイルシステム全体のスキャン（PHP + npm 双方）
- 現時点の判断: `composer audit` + npm `audit` で PHP/JS の供給チェーンはカバー可能。Trivy は Docker image scan が必要になった場合（Staging/本番コンテナ導入時）に追加評価する
- L4 carry: CARRY-ADR-021-002（後述）

#### F. Critical CSS 抽出ツール選定（GAP-RT-021 / PERF-CARRY-001 統合）

GAP-RT-021 で「Critical CSS 抽出・インライン化の仕様・トリガー条件が設計に存在しない」と指摘された。本 ADR にツール選定を統合する。

**P0 採用: `@critical-css/cli`（critical パッケージ）**

- パッケージ: `critical@^7.2`（npm dev dependency / CI 専用、フロント配布物に含まない）
- 動作: Puppeteer ベースでページをレンダリングし、Above-the-fold CSS を抽出してインライン化する
- 採用理由:
  - WordPress エコシステムでの実績（ThemeB / テーマA の設計参照先でも類似手法を採用）
  - `@wordpress/env` で立ち上げた WP インスタンスに対してそのまま実行可能
  - LCP < 2.5s 必達（REQ-NF-001b）への直結
- トリガー条件: `@wordpress/scripts` ビルド後、代表テンプレート（HP / LP / 記事 / アーカイブ）に対して CI で自動実行し、生成した critical CSS を `style-critical.css` として `dist/` に出力する
- ライセンス: MIT
- 代替:
  - **penthouse**: CLI ツールとして軽量だが Puppeteer 管理が `critical` と重複するため統一を優先して不採用
  - **critters**（webpack plugin）: `@wordpress/scripts` の webpack に組み込み可能だが、Full-Site Editing の動的テンプレート構造との相性を L4 で検証するまで PoC 保留

**PoC 保留: critters（webpack プラグイン）**

- `@wordpress/scripts` ビルドパイプライン内での CSS インライン化。FSE 動的テンプレートとの相性評価が必要
- L4 carry: CARRY-ADR-021-003（後述）

## L4 CI パイプライン構成（受入条件）

L4 で CI を組む際の通過条件を以下に定義する。**すべての P0 ツールが green であることが G4 通過の必要条件**。

```
PR マージ前 CI（G3〜G4 フェーズ）:
  ①  PHPCS (WPCS + PHPCompatibilityWP)     — ERROR 0
  ②  PHPStan level5 (baseline 差分)         — ERROR 0
  ③  composer audit (critical/high)          — 脆弱性 0
  ④  @wordpress/scripts build               — build EXIT 0
  ⑤  Ajv スキーマ検証                        — スキーマ全件 PASS
  ⑥  PHPUnit (Unit + Integration)           — FAIL 0
       └ opis/json-schema 検証ロジックを Unit でカバー
  ⑦  Playwright E2E (@wordpress/env 起動)   — P0 シナリオ全件 PASS
  ⑧  Lighthouse CI (代表テンプレート)        — LCP < 2.5s / INP < 200ms / CLS < 0.1
  ⑨  critical CSS 生成                      — dist/style-critical.css が 0 バイトでない
  ⑩  axe-core (TC-016 a11y basic check)     — 日本市場向け基本配慮の確認

release ビルド時（G6〜G7 フェーズ）:
  ⑪  CycloneDX SBOM 生成 (TC-027)          — sbom.cdx.json artifact 確定

週次 scheduled run:
  ⑫  composer audit (全 severity)           — report 生成・通知
  ⑬  PHPCompatibilityWP (PHP 8.5 RC)        — 先行互換確認
```

## Consequences

### 良い面

- PHP 8.1〜8.4 の互換 CI（GAP-RT-029/031）が確立され、WP7.0 対応の基盤が整う
- PHPStan level 5 により型安全性が向上し、WP フック引数の型不整合（GAP-RT-032）を PR 前に検出できる
- PHP / JS の JSON Schema 検証（GAP-RT-033/034）が統一され、`seo-profile.schema.json` 等の契約違反を CI で早期捕捉できる
- `composer audit`（GAP-RT-035）により OSSRA 相当の供給チェーン管理が CI に組み込まれる
- CycloneDX SBOM により TC-027（SBOM gate）が達成可能になり、Theme Review 提出前に artifact が確定する
- `critical` ツールによる Critical CSS 抽出が GAP-RT-021（PERF-CARRY-001）を解消し、LCP 必達（REQ-NF-001b）の CI 保証が整う

### 制約・リスク

- PHPStan level 5 + WP stubs は WP コア API 呼び出しの一部で false positive が発生しうる。初回 baseline 生成時に意図的な false positive を確認・除外することが必要
- `composer audit` は Composer Advisory Database の収録範囲（40,000+ パッケージ）を前提とする。WordPress.org 登録なしの小規模 Composer パッケージはカバーされない場合がある
- `critical` ツールは Puppeteer を必要とするため CI 環境に Chrome/Chromium インストールが必要（`@wordpress/env` 側に付随するケースが多いが、CI スペックに依存する）
- PHPCompatibilityWP は PHP 8.5 RC の最新ルールセットが公開タイミング依存のため、GA 前の週次 run では false negative が残る可能性がある

## L4 carry 登録

| carry-id | 内容 | 優先度 | 解消タイミング |

## Alternatives considered

- **Psalm**: PHP 静的型解析の代替候補。WordPress スタブの整備が phpstan-wordpress より遅れており、WP フック型の false positive が多い。PHPStan + szepeviktor/phpstan-wordpress の組み合わせが現時点では WordPress 向けに優れると判断し不採用
- **Snyk CLI**: SaaS 依存。無料枠の SLOC 制限（200K）と API キー管理のコストを勘案し、`composer audit`（ゼロ設定）+ CycloneDX（SBOM）で要件を充足できると判断し PoC 保留
- **penthouse**: Critical CSS 抽出ツール。`critical` と役割が同一であり重複管理になるため不採用。`critical` は Puppeteer 管理を内包しており導入コストが低い
- **security-checker（SensioLabs）**: 2022 年に EOL。不採用
