# ADR-027: WP 7.0 固有機能の採否凍結

- Status: Accepted
- Date: 2026-06-21
- Phase: L3 / Gate: G3
- 関連 GAP/CARRY: GAP-RT（WP7.0 完全性監査 §C）/ CARRY-WP7-013 / CARRY-WP7-014 / CARRY-WP7-015
- 参照 ADR: ADR-020（WP7.0 先回り/READ公開） / ADR-023（FSE転換・theme.json v3） / ADR-026（embed） / ADR-025（AI開示）
- 参照: docs/reviews/WP7-THEME-COMPLETENESS-AUDIT.md §2(C) / docs/research/wp-ecosystem-20260620.md

---

## Context

WP 7.0 GA（2026-05-20）後の完全性監査（§C）で、WP7.0 固有機能 6 種（Block Bindings / Interactivity API / Font Library / Section Styles / Speculative Loading / should_load_separate_core_block_assets）の採否が L2/L3 で未凍結であることが判明した。うち 3 種は CARRY-WP7-013/014/015 として L4 entry 必達 carry 化されている。

本 ADR は 6 種すべての採否を L3 時点で凍結し、AGENT-NEO テーマの WP7.0 対応方針（WP バージョン下限 6.6）を固定する。WP6.6-6.8 環境でのフォールバック検証は L4 carry（CARRY-WP7-004 と連動）で実施する。

## Decision

### D1 Block Bindings API（CARRY-WP7-013）

#### 採否

採用。WP7.0 で `block_bindings_supported_attributes` が追加される機能を前提とし、WP6.5+ の `core/post-meta` から段階的に拡張する。

#### 根拠

- WP 標準で構造化バインディングを実現でき、`REQ-NF-025` の責務分担（テーマ=計測 ID / メタ値を提供・束縛、Automation SEO=データ取得・判断）と整合。
- WP7.0 以降の `block_bindings_supported_attributes` filter を用いたカスタム属性追加は、既存 `core/post-meta` からの移行で将来運用性が高い。
- Pattern Overrides 自動対応により、セクション識別子や CTA 情報の宣言的更新設計が可能。

#### スコープ

- Phase1: `core/post-meta` を前提とした SEO 値 / `section_id` / `cta_id` のバインド。  
- WP7.0 時点: `register_block_bindings_source()` / Pattern Overrides を併用したカスタムソース登録。

#### 実装規律

- Block Bindings source 登録は `register_block_bindings_source()` を **`label` / `get_value_callback` / `uses_context`** で行う。値の解決は `get_value_callback` 内で実施し、`current_user_can()` によるアクセス判定はその中で行う。解決値は `transient` でキャッシュする。
- 束縛対象メタの登録は `register_post_meta()` / `register_meta()` 側で実施し、`show_in_rest: true`、`sanitize_callback`、`auth_callback` を設定する（`register_block_bindings_source()` の引数ではない）。
- AI が「採否」ロジックを持たない構成（`REQ-NF-025` 準拠）。

#### WP6.6-6.8 フォールバック

- バージョン上限 6.8 では `core/post-meta` のみ運用し、`WP7.0` 専用 API は未対応時は静的値（既存値）へ退避。
- 未対応版では未対応 API 呼び出しを行わず、バインドなしの静的レンダリングに degrade する。

---

### D2 Interactivity API（CARRY-WP7-014）

#### 採否

採用（性能予算内の限定利用）。

#### 根拠

- `@wordpress/interactivity`（Preact signals ベース）は React/Vue 非依存で、`REQ-NF-001a` の無駄 JS 最小化方針に整合。
- WP7.0 で `watch()` が追加されることを活用し、軽量インタラクションは本体側に集約できる。
- `React19` の巻き戻し影響を受けにくく、WP7.1 以降の再挑戦リスクも低減。

#### スコープ

- テーマ本体で必要な軽量 UI（FAQ トグル、アコーディオン、モバイルメニュー、セクション内簡易タブ等）に限定。
- 独自 JS フレームワーク（React/Vue）導入は行わない。
- `Embed` 系（iframe）との責務を分離し、テーマ本体インタラクションのみを対象とする。

#### 実装規律

- ページ種別別性能予算（`REQ-NF-001f`）を満たす範囲で導入。
- iframe payload/イベント予算と重複しないよう、DOM 操作対象を明確化。
- `reqs`: キーボード操作・フォーカス移動・`aria-*` 連動を満たし `CARRY-A11Y-001` 前提を満たす。

#### WP6.6-6.8 フォールバック

- 対応版でない環境では同等機能を static CSS/HTML + 既存イベント実装へフェイルセーフ化し、既存利用を阻害しない。
- ページタイプ別予算表に従い、未対応時は表示品質を維持して JS 非依存化を優先。

---

### D3 Section Styles（CARRY-WP7-015）

#### 採否

採用。

#### 根拠

- WP6.6+ の nested inner block / elements スタイル運用は、セクション単位バリエーションの命名規約を `theme.json/styles/*.json` partial 化して維持できる。
- `styles` partial の先頭 `blockTypes` により、カテゴリ別バリエーション選択を Automation SEO 連携で扱いやすくする。
- WP7.0 で button の `:hover/:focus/:focus-visible/:active` が拡張されるため、CTA・ボタン配色との整合が取りやすい。

#### スコープ

- `styles/` partial で `blockTypes` を明示したセクション系 variation を定義。
- Customizer 依存を避け、theme.json / style variation 前提で宣言型に統一。
- `core/button` の擬似要素拡張は既存 ADR（ADR-023 D-4）と整合して扱う。

#### 実装規律

- 既存 `design token` による命名・値定義で重複禁止（`ADR-010` 準拠）。
- 見た目コピーではなく、利用価値がある差分スタイルのみを variation 化。

#### WP6.6-6.8 フォールバック

- `blockTypes` 対応が限定される場合は、共通化レイヤを維持したまま `styles` 無効化ではなく静的代替クラスへ委譲し、崩れを避ける。

---

### D4 Font Library（A）

#### 採否

採用（既存決定の確認）。

#### 根拠

- `theme.json` の `settings.typography.fontFamilies` と `Font Library API`（WP6.5+）により、Customizer 系設計（`theme.json` 化方針）を継続できる。
- `ADR-023` のカテゴリ A 決定を確認的に固定する。

### D5 Speculative Loading（WP6.8）

#### 採否

採用（既存決定の確認）。

#### 根拠
- パフォーマンス系最適化方針（`REQ-NF-001` 系）と整合。
- 詳細実装は既存 L4 carry と ADR-023 系の運用に委譲。

### D6 `should_load_separate_core_block_assets`

#### 採否

採用（既存決定の確認）。

#### 根拠
- CSS 分離ロード戦略の要件として既に ADR-023 / A4 系に反映済み。
- JS 分離とは別に、コアブロック資産の条件読み込みを運用する。

## Consequences

- WP7.0 固有機能の採否を一括凍結し、L4 theme scaffold の設計入力を固定。
- D1/D2/D3 は新規 L4 implementation carry として解放し、D4/D5/D6 は既存決定参照として運用。
- 3 機能を `CARRY-WP7-013/014/015` 由来として解決扱いし、L4 での実装 carry のみに委譲する。
- WP6.6-6.8 の実運用検証が必須であり、`CI Tier A` の結果に応じて実装条件を補強する。

## Alternatives Considered

- **Block Bindings 非採用**（`render_callback` で都度 `post_meta` を組み立て）  
  `REQ-NF-025` の責務分担に反し、再適用時の保守負荷が増大するため不採用。
- **Interactivity API 非採用（vanilla.js）**  
  状態管理が分散し、性能予算管理・無駄 JS 制御が困難となるため不採用。
- **Section Styles 非採用（class 固定）**  
  セクション単位宣言の命名・選択が難しく、AI 命名付き変更（`S-DESIGN-TOKEN`）との連動が弱いため不採用。
