# フォームの確認・修正・失敗の再現

WT-FR-FORM-01A/Bの既存要求を、独立した一時固定ページにフォームブロックを置いて検証する。専用labのみ。氏名・メール・本文は架空値とし、試作は入力を保存・業務送信しない。実メールや業務処理を追加する計画ではない。

[確認と変更のデザインパターン](https://design-system.service.gov.uk/patterns/check-answers/)では、送信前に回答を見直し、修正できる経路を設ける。[WordPressのnonce検証](https://developer.wordpress.org/reference/functions/wp_verify_nonce/)は不正なnonceをfalseとする。今回の確認は、画面の存在だけでなく、修正時の値保持と無効な入力の拒否を照合する。

`node scripts/verify-form-flow.mjs --baseline`で変更前、引数なしで変更後を検査する。PC1440/SP375、JS有無、確認あり/なし/同一ページ見直しの12条件。必須項目の不備、氏名・メール・改行を含む本文の修正時保持、修正後の再確認と完了、不正nonce、未知の段階、正規化すると有効になる段階、配列の段階指定を確認する。一時ページはfinallyで削除する。ブラウザからの外部POST試行を数えるが、これだけでサーバー側の全外部通信やDB非保存を保証しない。

初期検査の横溢れは遷移/描画待ちが不十分な可能性がある。`initial-baseline.json`は最初の測定、`navigation-baseline.json`は描画待ち中断でcompleted=falseの記録。JS無効でも完了要素とネットワークの静止を待ってから再測定する。途中実行や待機方式の誤りを製品の改善率へ算入しない。

修正対象は`wt_form_state`の段階指定。従来はsanitize_keyで入力を変換し、input/back以外は完了へ進んでいた。input/back/confirmの文字列だけを許可し、未知・配列・変形した値は入力とエラーへ戻す。正式な入力検証・nonce判定を維持する。PoCの段階表示の修正であり、セッション付きの実業務申込管理を実装した意味ではない。

未確認: 全9種別と全項目の入力境界、段階式レイアウト、別ページ完了、LP/イベントへの選択的配置、実処理/第三者フォームとの共存、実際のnonce有効期間の経過。イベントは`patterns/event.php`の固定ステータスをCSSで切り替える段階で、期限・満席・受付前の自動遷移を確認したものではない。専用の時刻/残席fixtureが引き続き必要。

最終結果: 修正前の有効な基準測定は198検査中72失敗（不正段階の拒否36件・入力値保持36件）。描画静止後は横溢れなし。修正後はエラーからの再開20検査を追加した218検査がすべて成功。`verify.json`とPC/SPの`error-*.jpg`・`done-*.jpg`を保存し、FORM-01A/Bを部分確認として対応付けた。初期の横溢れ4件と描画待ち中断は製品の改善件数に数えない。

追加検証: `node scripts/verify-form-kinds.mjs`。9種別と全項目セットをPC/SP・JS有無の40条件で操作し、282検査が成功。必須未入力、正常値の確認・修正時全送信値保持、完了種別、添付nameなし、完了時横溢れを照合。一時ページは削除済み。`kinds-verify.json`をFORM-01A/Bへ追加。各型の異常値・境界値、段階式、別ページ完了とLP/event配置は引き続き未完了。

追加する検証範囲: 段階式レイアウトでは9種別＋全項目セット、PC/SP・JS有無の40条件を`verify-form-steps.mjs`で操作する。JSありは各段の次へ・戻ると全値保持、JSなしは全項目の同時入力、両者で確認からの修正と別ページ完了への種別継承を確認する。初回は検証スクリプトの入力探索がフォーム外の非表示検索欄まで含み中断した。探索範囲をフォーム内へ修正後、395検査が成功。製品の不具合修正としては数えない。

LP/イベントは`verify-form-slots.mjs`で一時ページに明示テンプレートを割り当て、PC/SP・JS有無で既定のフォームブロック不在、選択時の項目集合、必須不備、全値保持、別ページ完了を確認する。イベントはform_kind:contactを与えてもapplyを継承することを照合。既存の同名fixtureは上書きせず停止する。/thanks/が未作成の場合だけ専用labに一時作成し、作成分だけ削除して不在を再確認する。第三者フォームの外部処理や全テンプレート割当境界の証明ではない。

配置検証結果: 83検査すべて成功。FORM-01A/Bへsteps395・slots83の証拠を追加し、部分確認を維持。各入力型の異常値境界、全配置型の視覚/通信、全テンプレート解決境界、サーバー非保存/非送信の全経路は未完了。

異常値境界の実機検査: 全項目セットを正常値で埋めた後、1項目ずつ直接POSTを置換する。日付の実在性（2月30日、13月、年0）、希望日、人数の小数/0、列挙外の選択肢、メール不一致、電話・郵便・かな、ホストなしURL、同意の不正値、captchaを対象とする。PC/SP・JS有無は元画面の準備条件で、直接POSTがクライアント検証を通ったという意味ではない。根拠: [PHP checkdate](https://www.php.net/manual/en/function.checkdate.php) の暦日検証、[date入力](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/date) と [number入力](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/number) の入力型とサーバー検証の必要性。人数は既存min=1/step既定1、同意は既存value=1に合わせる。業務上の日付範囲や受付期限は別の要求であり、この検査で任意の上限を決めない。

実機の基準測定は94検査中36失敗（9種類×4画面条件）。実在しない日付・年月・希望日、人数の小数、ホストなしURL、同意の任意文字列が確認段階へ進んだ。修正はPHPで暦日をcheckdateにより検証し、希望日のキーを0〜2に限定、人数を正の整数、URLをHTTP(S)の有効なURL、同意をvalue=1へ限定する。JSにも暦日・整数・URL・同意値の検証を反映。過去日・受付期限・定員など業務上の範囲は追加していない。基準測定にない正常値対照を追加した初回修正後98検査は成功。最終検査は閏日・有効月とJS側の小数拒否を追加し、既存4経路を再実行して証拠の鮮度を確認する。

最終結果: boundaries112、flow218、kinds282、steps395、slots83の計1090検査が成功。JS小数拒否はブラウザPOST試行0も照合。PHP構文、JS構文、要求整合性、consumer health成功。全受入の部分確認を維持し、既存4証拠を現ソースのハッシュで再取得した。
