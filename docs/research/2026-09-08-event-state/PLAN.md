# イベントの受付時刻・残席fixture

対象は既存 WT-AC-EVENT-01A/B。クエリで表示を切り替えるだけでは、期限・満席・受付前の遷移を確認したことにならない。

現行のpatterns/event.phpは受付中・残席わずか・受付終了の静的HTMLを持ち、event_status軸のCSSで選ぶ。受付時刻・定員・申込数を読む処理はこのパターンにない。専用labの一時イベントページへ、試験用メタ `_wtcf_event_fixture` として受付開始・締切・定員・申込数・観測時刻を置き、クエリでevent_statusを指定せず描画を確認する。このメタは今回提案する試験入力であり、製品の既存契約ではなく、現行コードには未接続である。

試験条件は受付開始の1秒前と開始時刻、定員50に対する申込50と49、締切1秒前と締切時刻。境界の候補は開始を含み締切を含まない。満席解除時は受付中へ戻る。残席わずかの閾値、無効な時刻・負の定員、取消・中止、タイムゾーン、同時申込や定員の予約処理は別途整理が必要。業務上の定員更新や外部チケット送信は今回の表示fixtureに含めない。

`node scripts/verify-event-state.mjs` は不足を測る基準実行。`--strict`は期待と不一致なら失敗終了する。6状態×PC/SPとfixture削除の13検査。基準結果で受付中の表示が期待と一致しても、メタを読んだ証明にはならないため受入完了には対応付けない。次段でfixtureを受け取る表示経路と受付不能時の導線を実装し、同じ入力群で遷移を検証する。既存のクエリ式デザイン比較は保持する。

基準結果: 13検査中6不一致。受付前・満席・締切時刻のPC/SPで受付中のまま。一時ページの削除を確認。受付中と期待が一致する残り6行は未接続の既定表示と偶然一致しただけであり、遷移成功に算入しない。

実装中の表示経路: inc/event-state.phpでメタの開始/締切/観測時刻/定員/申込数を読み、受付前→受付中→満席/受付終了を判定する。観測時刻の差替えは専用labだけで、通常環境は実時刻を用いる。フォームの処理前に同じ状態を照合し、受付不能なら完了へ進めない。パターンでは受付不能時に申込フォーム全体を描画せず、状態説明と開催情報へのリンクを残す。fixtureがない既存デザインは保持する。

検証: 6状態×PC/SP×JS有無で、状態ラベル、フォーム有無、理由、#applyへの移動、直接POSTの可否とfixture削除の121検査成功。4状態のPC/SPを撮影。既存フォーム5検証は新しい依存event-state.phpのhashも含めて再取得する。無効メタ・時刻形式・タイムゾーンの全境界、全デザイン軸、地図とサイドバー、実予約の同時実行は未完了。

Claudeへはハーネスメモリの正規PR通知と、未コミット差分の対象hash付き通知を投入済み。通知投入とレビュー完了を区別し、応答未確認の段階ではクロスレビュー済みとしない。

境界検証の追加: `verify-event-boundaries.mjs`で17入力×PC/SP×JS有無を照合。UTCと+09:00/-05:00の同一時刻、開始/締切、不正暦日、ゾーン欠落、offset時/分の範囲外、観測時刻欠落、期間逆転/同時刻、定員/申込数の型・負値・0・超過を対象とする。時刻文法の根拠は [RFC 3339 §5.6](https://www.rfc-editor.org/rfc/rfc3339#section-5.6)。現在のfixtureは秒単位・明示offsetの限定形式であり、RFC全形式・閏秒・地域タイムゾーン名への対応を主張しない。
