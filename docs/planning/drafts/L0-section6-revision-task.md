## 修正必須事項（ブロッカー 3 件）

### P1-01: X 投稿導線の Phase 整合

L1/NSRM の Phase 配分（正本）：

- **REQ-F-018**（SNS 連携基盤）: Phase 1。シェアボタン + OGP + 記事公開時の SNS 接続面のみ Phase 1。**自動投稿は Phase 2 送り**（nsrm-08 の判断、SNS API 仕様変更リスク排除のため）
- **REQ-F-019**（法人版 SNS 深い統合）: Phase 2
- **REQ-F-020**（SNS API 認証情報管理）: Phase 2（P1）

→ ドラフト §6.2 X 主力 SNS、§6.3 自社運用フロー、§6.6 Phase 1 ローンチで必要な機能 の各記述で、**X 自動投稿が Phase 2** であることを明示する。Phase 1 は「シェア導線 / OGP / X Card / 手動投稿運用」のみ。

§6.3 のループ図にある `X 投稿導線（記事公開時）→ X 流入` は、Phase 1 では「OGP + 手動投稿 + 共有導線」、Phase 2 で「自動投稿に拡張」と注記する。

### P1-04: Phase 1 ローンチセット件数

正本値は `nsrm.yaml metrics.phase_1_count: 23`（TL レビュー反映で F-041 が Phase 1 昇格）。

→ §6.6 の冒頭「現時点の 22 件は」を **「現時点の 23 件は」** に修正。F-041（記事編集経路）が Phase 1 に含まれることを反映する。§6.6 のグループ表「反映安全性 | REQ-F-021 / REQ-F-041 / REQ-F-042」は既に F-041 を含んでいるが、件数が 22 のままなので不整合。

### P1-05: 公開指標の法務ガード

§6.4 の live counter / 公開ダッシュボードに対して、§6.8 の直前または §6.4 末尾に **「公開指標ポリシー」表** を新設する。表に以下の列を含める：

| 公開項目 | 公開可否 | 匿名化単位 | 公開遅延 | 集計閾値 | 保存期間 | 根拠ログ要否 | 同意取得要否 | 表示責任者 |
|---|---|---|---|---|---|---|---|---|

代表行として以下を含める（具体値は PO/法務で確定するため「要確認」可）：

1. 自社サイト LCP 中央値
2. 直近 30 日の記事公開本数
3. 直近 30 日の更新頻度
4. CTA 改善履歴の前後差分（数値のみ・顧客特定なし）
5. テーマ累計販売数（仮）
6. S1 累計案件数（仮）
7. 顧客名・個別 CV・個別ユーザー行動（=> 公開不可）

加えて以下の制約条文を §6.4 末尾または §6.8 リスク表に明記：

- **個人情報保護法**: 個人を特定できる情報・端末情報の公開禁止。自社サイト訪問者の個別行動は集計値のみ
- **景表法**: 「実績」「効果」表現には根拠ログと算出条件を併記。誇大表現禁止
- **特商法**: 販売実績の表示責任者・連絡先・取引条件を明記
- **GDPR / EU 訪問者**: 個別追跡データを EU 域外サーバーで処理する際の同意取得経路（cookie consent）
- **同意取得**: 公開対象に含める計測データは「公開計測同意」を ToS / プライバシーポリシーに明記
- **公開遅延**: リアルタイム公開を避け、最低 24h 以上の遅延公開とする（推奨。要 PO 確認）

## 軽微修正（4 件、同時反映）

### M1: §6.5 の「高 / 中 / 条件付き」を「成立条件 / 向いている前提」に変更

Q-002 の PO 決裁余地をさらに明確化する。「推奨度」列を「成立条件」または「向いている前提」に書き換え、各選択肢が前提次第で成立する書き方に修正。

### M2: §6.3 自社運用ループを Phase 1 / Phase 2 で分離

「H2 編集 / 要素 swap / A/B variant 改善」の各ステップは Phase 2 機能（F-022/F-023/F-024）。Phase 1 のループでは利用できない。

→ ループ図を 2 段に分け、**Phase 1 ループ**（記事 CRUD + OGP + 計測 + 手動 X 投稿 + SEO 改善）と **Phase 2 拡張ループ**（H2 編集 / 要素 swap / 自律 A/B / X 自動投稿）を明示する。

### M3: Threads / LINE 公式の二層表現

「販促主戦場ではない（Phase 1 では使わない）」が「製品 capability としては将来保持する（Phase 2 で深い統合）」と二層構造で書き換える。

### M4: §6.8 に「競合模倣リスク」「障害時の静的フォールバック導線」を追加

| リスク | 影響 | 対応方針 |
|---|---|---|
| 競合模倣リスク | 公開する機能説明から導線設計・改善観点が読み取られ、競合に実装手法が伝わる | 公開する機能説明は原理レベルに留め、内部運用ノウハウ（具体的なプロンプト・variant 生成ルール・改善判断基準）は開示しない |
| 障害時のブランドリスク | 自社サイト障害が「AGENT NEO 製品の品質不足」と読まれる | staging / 静的フォールバック導線（事前ビルド済み静的 HTML への即時切替）/ 障害時の販売 LP 代替経路を準備し、「Built with AGENT NEO」表示中のサイトが落ちないことを担保 |
