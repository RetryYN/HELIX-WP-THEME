## 目的

L0 企画書 [§6 戦略・販売ファネル](../L0-planning.md#L764) は現状「製品ファネル（移行プラグイン → S1 → テーマ購入）」しか書かれておらず、PO（ユーザー）が想定している以下の**流入・運用戦略が完全に抜けている**。これを埋める拡張ドラフトを作成する。

## PO の指示（核心、絶対に外さない）

1. **基本戦略は「SEO + X」を Automation SEO で運用して展開する**
   - 自社サイトを SEO 流入の主戦場にする（記事 / BLP / LP の検索評価）
   - X（旧 Twitter）を主力 SNS チャネルにする（自動投稿 / 自社アカウント / 引用 RT 戦略）
   - これらを **Automation SEO** で運用（記事生成 / SEO メタ最適化 / A/B / variant 改善ループ）

2. **MVP 概念は採らない**
   - 「最小限で出して様子見」「ベータユーザー募集」「α 版リリース」の発想は持ち込まない
   - Phase 1 は「ローンチ可能な完成セット」を意味する。「最小限で検証」ではない
   - 文書中で「MVP」という語を使わない（`Phase 1 ローンチセット` または `Phase 1 完成版` と表記）
   - 「検証仮説」「実験」「pilot」のような言葉も避ける

3. **サイトがプロモーションを兼ねる**
   - 自社サイト = AGENT NEO の実装そのもの = 販売 LP = live demo
   - 「製品の機能」と「販売 LP の機能」が同一物（ドッグフーディング）
   - サイトが動かない = 売れない構造。だから機能削減で MVP 化する判断は破綻する
   - 自社サイトの計測データ（CV / CTR / 流入）が販売訴求の最強根拠

## ドラフトに含めるべき必須セクション（H3 単位）

### §6.1 グロース戦略の基本原則
- ドッグフーディング前提（自社サイト = 製品 = 販売 LP）
- 「MVP を出して様子見」を採らない理由（自社サイトが動かないと集客できない構造）
- Phase 1 ローンチ = 自社サイト稼働 = 販売開始

### §6.2 流入チャネル設計
- **SEO（主軸）**
  - 記事 / BLP（記事 LP）/ 法人 LP / 個人版アフィリ向け解説記事
  - キーワード戦略の方針（例: 「WordPress AI テーマ」「AI で運用 WP テーマ」「AGENT NEO」「WP テーマ + Automation SEO」など）
  - 第一原理 2（ページタイプ別性能予算）が SEO 評価に直結する根拠
  - LLMO（AI 検索引用最適化）が将来の流入を支える設計
- **X（主力 SNS）**
  - 自社アカウント運用（製品アップデート / 機能解説 / 顧客事例）
  - **自動投稿**: AGENT NEO の F-018（Phase 1）+ F-019（Phase 2）で実装される機能を自社運用で最初に検証
  - 引用 RT 戦略・コミュニティ形成（WP 開発者・アフィリ・法人マーケ）
  - X カード（OGP）最適化
- **オプション**: Threads / LINE 公式（Phase 2 で深い統合 = 法人版の販売チャネル）
- **採らないチャネル**: 有料広告（初期）・PR Times（初期）— 理由を明記

### §6.3 自社運用フロー（Automation SEO ループ）
```
自社サイト（AGENT NEO 本番運用）
  ↓
記事ネタ抽出（Automation SEO LLMRouter）
  ↓
記事生成 → AGENT NEO に POST（agent-neo/v1）
  ↓
H2 編集・要素 swap で AI 自律改善
  ↓
A/B variant で CTA / Hero 改善
  ↓
seo-tool-connector で計測 → Automation SEO に集計
  ↓
勝者採用 / loser kill
  ↓
X 自動投稿（記事公開時）→ X 流入
  ↓
SEO 流入も継続強化（answer unit / evidence graph）
  ↓
CV（テーマ購入 / S1 問い合わせ / Open Editor Bridge 申込）
  ↓
顧客行動データ → 次サイクルの記事ネタへフィードバック
```
このループ自体が「AGENT NEO + Automation SEO の機能デモ」になっている設計を明記。

### §6.4 サイト = 販売 LP の構造
- 自社サイトのページ構成案（HP / サービス LP / 移行プラグイン LP / 個人版 LP / 法人版 LP / 開発ブログ / 顧客事例）
- 各ページが製品のどの機能を実証しているかのマッピング
- 「このサイト自体が AGENT NEO で動いている」表示の設計（"Built with AGENT NEO" バッジ等）
- 自社サイトの計測データを販売訴求に使う仕組み（live counter / 公開ダッシュボード等の検討）

### §6.5 ローンチ順序の方針
- 個人版先行 / 法人版先行 / 同時 のいずれが PO 想定の自社運用と整合するか考察
- 自社サイトが「個人ブログ寄り」なのか「法人 LP 寄り」なのかで答えが変わる
- PO の Q-002 判断材料として論点を整理（決定はしない、PO に委ねる）

### §6.6 Phase 1 ローンチで必要な機能（MVP ではない）
- 自社サイト稼働に必要な機能リスト（NSRM Phase 1 22 件と差分があるか）
- 「ローンチ前に絶対欠けてはいけない」機能の根拠を自社サイト運用視点で書く
- nsrm.yaml の `phase_1_mvp` キー（命名は HELIX 標準で残置、意味は「Phase 1 ローンチセット」と読み替え）

### §6.7 グロース KPI（数値目標は PO 確定事項として保留）
- 計測すべき指標のリスト（流入数 / X フォロワー / 記事 PV / CV / テーマ販売数）
- 数値目標自体は PO が後日決定する OPEN QUESTIONS として追加（Q-011 として提案）

### §6.8 リスクと対応
- 自社サイト障害 = 販売停止リスク → 冗長化 / staging / rollback
- Automation SEO 障害 = ループ停止リスク → 手動運用フォールバック
- X API 仕様変更リスク → adapter 層で吸収（既に F-020 で予定）
- SEO スパム判定リスク（AI 大量生成記事）→ Automation SEO の品質ゲート
