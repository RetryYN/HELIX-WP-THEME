## 6. 戦略・販売ファネル

### 6.0 製品ファネル（既存）

```text
無料プラグイン（プラン A 機械変換）
   ↓ ユーザー自身がプランを選択
プラン B（AI フルセットアップ）= S1 サービス課金
   ↓
受け皿: AGENT NEO テーマ（個人 ¥19,800 / 法人 ¥98,000）
追加収益: Automation SEO 別課金 / S1 / 有料アドオン / 従量課金
```

**戦略的旨み:**
- 無料プラン A = lead magnet。間口最大化・wp.org 公式ディレクトリ経由の自然流入
- プラン B = AI 再構築の独自価値で課金（Automation SEO の既存 LLMRouter を活用）
- 個人/法人テーマ = 受け皿。アップグレードパスで LTV 拡大
- ユーザーが自分でプランを選択 → 押し売り感ゼロ・納得感の高い購買体験
- テーマ別アダプタ不要 → 全テーマ即対応の宣伝が打てる + 開発・保守コスト削減

### 6.1 グロース戦略の基本原則

AGENT NEO の販売は、テーマを売るための別サイトを作る構造ではなく、**自社サイトそのものを AGENT NEO で稼働させ、その運用成果を販売根拠に変える構造**を採る。自社サイトは「製品紹介ページ」ではなく、AGENT NEO の HP/LP/BLP/SEO/LLMO/計測/A-B 改善を本番で回している **live demo** である。

この前提では、自社サイトが十分に動かない状態で先に販売を始める判断は成立しない。なぜなら、サイトが止まることは同時に販売導線と証拠の停止を意味し、検索流入・X 流入・問い合わせ・テーマ購入が同時に弱くなるためである。したがって Phase 1 ローンチは「最初に出せる形」ではなく、**自社サイトを本番運用しながら販売開始できる完成セット**を意味する。

本章では価格戦略や競合比較は再掲せず、流入・運用・自社実証ループに限定して追記する。価格の妥当性は [価格戦略と売れる理由](../../../解析レポート/09-価格戦略と売れる理由.md)、市場ポジションは [競合テーマ総合評価と市場ポジション](../../../解析レポート/26-競合テーマ総合評価と市場ポジション.md) を参照する。

### 6.2 流入チャネル設計

AGENT NEO の初期グロースは **SEO を主軸、X を主力 SNS** とする。両者を分離せず、Automation SEO が記事生成、SEO メタ最適化、共有導線運用、改善計画までを一連の運用として扱う。Phase 1 は共有導線/OGP/X Card/人手投稿（WP 運用者が共有導線から X へ手動で投稿する運用）を扱い、X 自動投稿は Phase 2 へ送る。

| チャネル | 役割 | 主なページ/施策 | AGENT NEO が同時に示す価値 |
|---|---|---|---|
| SEO | 主軸流入 | 記事、アーカイブ、BLP、法人版 LP、移行プラグイン LP、顧客事例 | ページタイプ別性能予算、SEO Core、LLMO、計測、内部導線 |
| X | 初速拡散と継続接点 | 製品更新、機能解説、記事公開、引用 RT、事例紹介 | Phase 1 は OGP/X Card、共有導線、人手投稿。Phase 2 で自動投稿へ拡張 |
| Threads | Phase 1 の販促主戦場ではない / Phase 2 capability | 短文要約、開発進捗、再掲導線 | Meta 系チャネル拡張の adapter 設計を保持し、深い運用は Phase 2 |
| LINE 公式 | Phase 1 の販促主戦場ではない / Phase 2 capability | 法人向け問い合わせ、資料請求、継続接点 | 法人版の深い統合、チャネル別 CV 計測は Phase 2 |
| 有料広告 | 初期は採らない | 検索広告、SNS 広告 | 訴求文より先に、自社運用実績を蓄積すべき段階 |
| PR Times | 初期は採らない | プレス配信 | 一過性流入より、検索資産と自社運用証拠の蓄積を優先 |

**SEO（主軸）**

- 記事は集客面、BLP は記事流入からの送客面、法人 LP は購入面、個人版の収益化ブロックは記事/アーカイブ上の購入導線を担い、全ページを自社テーマ上で統一運用する。
- キーワード方針は 4 層で設計する。
  - 問題起点: `WordPress AI テーマ`、`AI で運用 WP テーマ`
  - 製品カテゴリ起点: `WP テーマ Automation SEO`、`AI 運用型 WP テーマ`
  - 指名起点: `AGENT NEO`
  - 比較/導入起点: `法人 LP WordPress AI`、`アフィリエイト WordPress AI テーマ`
- 第一原理 2 の「ページタイプ別性能予算」は SEO 評価と直接つながる。記事/BLP/アーカイブは検索流入の主戦場であり、LP 用の重い JS や外部スクリプトが記事面へ漏れると、LCP/INP/CLS が悪化して流入基盤自体が弱る。AGENT NEO は `page_type` 単位の予算分離で、この漏れを構造的に防ぐ。参照: [L0 企画書 §1.1.1](../L0-planning.md)、[L1 要件定義 REQ-F-029 / REQ-NF-001f](../../requirements/L1-requirements.md)
- LLMO は将来流入の下支えとして扱う。`answer unit`、`evidence graph`、`citation anchor`、`AI visibility policy` を備えたページは、通常検索だけでなく AI 検索の引用面でも優位になりやすい。参照: [LLMO時代のテーマ設計重要観点](../../../解析レポート/24-LLMO時代のテーマ設計重要観点.md)

**X（主力 SNS）**

- 自社アカウントは「告知専用」ではなく、製品更新、機能の使い方、改善前後の差分、顧客事例、公開記事の再配信を担う。
- 記事公開時の X 導線は自社運用で先行利用する。Phase 1 は **共有導線、OGP/X Card、人手投稿** を最優先にし、**自動投稿は Phase 2** に送る。複数アカウント管理、法人向け深い統合、SNS API 認証情報管理も Phase 2 に含める。
- 引用 RT はコミュニティ接続に使う。対象は WP 開発者、アフィリエイター、制作会社、法人マーケ担当、SEO 実務者とし、「自社で回した運用結果」を話題の中心に置く。
- OGP/X Card は販促画像ではなく、記事・LP・事例ごとに訴求を切り替える流入口として扱う。X 上での見え方も AGENT NEO の実装品質の一部である。
- Threads / LINE 公式は販促主戦場としては Phase 1 で使わないが、製品 capability としては保持する。Threads の深い運用、LINE 公式連携、複数アカウント管理、チャネル別 CV 計測は Phase 2 で拡張する。参照: [nsrm.yaml](../../../.helix/nsrm.yaml)、[L1 要件定義](../../requirements/L1-requirements.md)

**初期に採らないチャネル**

- 有料広告は初期の主戦場にしない。理由は、広告最適化より先に自社サイトの自然流入・CV・A-B 改善データを販売根拠として蓄積する方が、製品と販売の一体運用に整合するためである。
- PR Times も初期の主戦場にしない。理由は、一過性の到達より検索資産・指名検索・X 継続接点の方が再利用性が高く、ドッグフーディング構造と相性が良いためである。

**Phase 2 拡張ループ**

```text
Phase 1 ループ
  ↓
H2 編集                                     [REQ-F-022]
  ↓
要素 swap                                   [REQ-F-023]
  ↓
自律 A/B で CTA / Hero 改善                 [REQ-F-024]
  ↓

  ↓
勝者採用 / 非採用 variant 停止
```

このループの重要点は、**運用行為そのものが製品デモになっている**ことである。見込み客は説明資料ではなく、自社サイト上で「記事が公開される」「計測される」「X と検索へ流れる」「次の改善へ戻る」という連続運転を見る。Phase 1 では販売導線と運用継続性を示し、Phase 2 で AI 自律改善と自動投稿まで拡張する。そのため、Automation SEO と AGENT NEO の責務分担は見せ方でもある。Automation SEO は判断と改善計画、AGENT NEO は本番反映と安全な実行基盤を担う。

また、このループは単なる集客ではなく、販売根拠の蓄積でもある。どの CTA が押されたか、どの LP が CV したか、どの BLP が自然流入を獲得したかを自社で持てるため、営業資料や LP 文言に「自社で回している数字」を直接反映できる。

### 6.4 サイト = 販売 LP の構造

自社サイトは複数ページの寄せ集めではなく、製品機能の実証面をページ単位で分担する構造にする。

| ページ | 主対象 | 販売上の役割 | 実証する AGENT NEO 機能 |
|---|---|---|---|
| HP | 全訪問者 | ブランドハブ、導線分配 | HP blueprint、Entity Graph、ページタイプ別性能予算、計測 |
| サービス LP | 法人見込み客 | 問い合わせ・資料請求獲得 | LP blueprint、CTA、フォーム、variant、A-B 改善 |
| 移行プラグイン LP | 既存 WP 運営者 | 無料導線、lead magnet | 移行導線、比較訴求、段階導線 |
| 個人版導線（記事 / アーカイブ） | アフィリエイター | 個人版購入導線 | 収益化ブロック、商品カード、関連記事送客、CTR 計測 |
| 法人版 LP | 企業・代理店 | 法人版購入/S1 導線 | 法人 HP/LP/BLP、問い合わせ、信頼訴求、risk guard |
| 開発ブログ | SEO 流入層 | 指名検索と信頼形成 | 記事生成、H2 単位更新、LLMO、公開スナップショット |
| 顧客事例 | 導入検討層 | 根拠提示、比較の決め手 | evidence graph、事例構造化、CV 計測、引用しやすい要約 |

自社サイト上には「このサイト自体が AGENT NEO で動いている」ことを明示する導線を持たせる。候補は `Built with AGENT NEO` バッジ、フッター表記、機能説明ページへの導線、該当ページで使っている機能の注記である。単なるロゴ掲出ではなく、「この LP は法人 LP blueprint」「このブログは BLP 導線込みで運用」「この事例ページは answer unit/evidence graph を使用」のように、ページと機能を結び付けて見せる。

自社サイトの計測データは販売訴求にも利用する。候補は、匿名化した live counter、公開ダッシュボード、記事/LP の改善履歴、直近期間の CTA 変化、LCP 中央値、公開本数、更新頻度である。ただし、顧客名・個別 CV・内部運用情報を含む公開は避け、公開範囲は PO/TL/法務で固定する。

**公開指標ポリシー**

| 公開項目 | 公開可否 | 匿名化単位 | 公開遅延 | 集計閾値 | 保存期間 | 根拠ログ要否 | 同意取得要否 | 表示責任者 |
|---|---|---|---|---|---|---|---|---|
| 自社サイト LCP 中央値 | 条件付き公開 | サイト全体またはページタイプ単位の集計値 | 24h 以上遅延公開（推奨、要確認） | 要確認 | 要確認 | 要 | 要確認 | PO / 法務 / 運用責任者 |
| 直近 30 日の記事公開本数 | 公開可 | 日次または週次集計 | 24h 以上遅延公開（推奨、要確認） | 要確認 | 要確認 | 要 | 要確認 | PO / 運用責任者 |
| 直近 30 日の更新頻度 | 公開可 | 日次または週次集計 | 24h 以上遅延公開（推奨、要確認） | 要確認 | 要確認 | 要 | 要確認 | PO / 運用責任者 |
| CTA 改善履歴の前後差分（数値のみ・顧客特定なし） | 条件付き公開 | ページ群または CTA 種別単位の集計差分 | 24h 以上遅延公開（推奨、要確認） | 要確認 | 要確認 | 要 | 要確認 | PO / 法務 / 運用責任者 |
| テーマ累計販売数（仮） | 条件付き公開 | SKU 単位の累計値 | 日次以上の遅延公開（要確認） | 要確認 | 要確認 | 要 | 要確認 | PO / 販売責任者 |
| S1 累計案件数（仮） | 条件付き公開 | 月次または四半期集計 | 日次以上の遅延公開（要確認） | 要確認 | 要確認 | 要 | 要確認 | PO / 販売責任者 |
| 顧客名・個別 CV・個別ユーザー行動 | 公開不可 | 該当なし | 該当なし | 該当なし | 該当なし | 要 | 要 | PO / 法務 |

公開制約は以下で固定する。

- **個人情報保護法**: 個人を特定できる情報・端末情報の公開を禁止し、自社サイト訪問者の行動は集計値のみを扱う。
- **景表法**: 「実績」「効果」表現には根拠ログと算出条件を併記し、誇大表現を避ける。
- **特商法**: 販売実績を表示する場合は、表示責任者、連絡先、取引条件を明記する。
- **GDPR / EU 訪問者**: 個別追跡データを EU 域外サーバーで処理する場合は、cookie consent を含む同意取得経路を前提とする。
- **同意取得**: 公開対象に含める計測データは、ToS / プライバシーポリシーに「公開計測同意」を明記した範囲のみを使う。
- **公開遅延**: リアルタイム公開は避け、最低 24h 以上の遅延公開を原則とする。最終値は PO 確認事項とする。

### 6.5 ローンチ順序の方針

Q-002 の判断材料として、ローンチ順は自社サイトの主たる顔つきと整合させる必要がある。

| 選択肢 | 整合しやすいサイト像 | 成立条件 | 向いている前提 |
|---|---|---|---|
| 個人版先行 | 記事 / アーカイブ 中心、アフィリエイト寄り | SEO 記事資産（記事 + アーカイブ + 商品カード）を厚く作りやすい。個人版の固定テンプレ構成（REQ-F-016）と収益化ブロック（REQ-F-030）を早期に live demo として見せられる。 | 法人向け高単価訴求の証拠が後ろ倒しになる。法人 LP/BLP の証拠は法人版ローンチまで作れない。記事 / アーカイブを初期 IA の主役に置き、検索資産の積み上げを優先する場合。 |
| 法人版先行 | HP/LP 中心、問い合わせ・資料請求寄り | 自社サイト = 販売 LP = live demo の論理が最も強い。高単価訴求と S1 導線が作りやすい。 | 記事量産だけでは証明しにくい運用品質も先に求められる。法人 LP と S1 導線を自社サイトの主役に置き、販売根拠を早期に見せたい場合。 |
| 同時ローンチ | HP/LP と記事運用を同時に厚く回す | SKU 間の説明が一貫し、後で IA を組み直しにくい。 | Phase 1 ローンチセットの負担が最も大きい。証拠作りも二面展開になる。初期 IA、運用体制、公開根拠の密度を同時に満たせる場合。 |

上記いずれを選んでも成立しうる。決定要因は「自社サイトの初期 IA を法人 LP 寄りで設計するか、記事/アーカイブ寄りで設計するか」である。前者を選べば法人版先行、後者を選べば個人版先行が機能・証拠面で整合する。同時ローンチは Phase 1 ローンチセットの完成条件と公開時の証拠密度を二面同時に満たす必要があり、運用負荷が最も大きい選択肢になる。決定は PO に委ねる。

### 6.6 Phase 1 ローンチで必要な機能

現行 `nsrm.yaml` の `phase_1_mvp` キーは HELIX 標準命名として残置されているが、本企画では **Phase 1 ローンチセット** と読み替える。現時点の 23 件は、自社サイトを本番運用しながら販売開始する観点でも大筋で妥当であり、**大きな機能追加差分はない**。ただし、単に「載っている」だけでなく、自社運用ループにどう効くかを明示して扱う必要がある。ここには `REQ-F-041`（記事編集経路）を含む。

| グループ | 対象 | 自社サイト運用で欠けてはいけない理由 |
|---|---|---|
| 基盤 | REQ-F-001 / REQ-F-002 / REQ-F-003 / REQ-F-025 | サイト本体を AI が安全に触れ、JSON 契約で一貫運用する前提になる |
| SEO/流入 | REQ-F-011 / REQ-F-029 / REQ-F-017 | 検索主戦場の記事/BLP/LP の表示品質と流入品質を守る |
| 計測/連携 | REQ-F-006 / REQ-F-007 / REQ-F-026 / REQ-F-027 | 計測がなければ改善根拠が残らず、Automation SEO と販売訴求がつながらない |
| 法人導線 | REQ-F-005 / REQ-F-012 / REQ-F-013 / REQ-F-031 | 自社サイトを法人向け販売 LP として使う場合の必須構成 |
| 個人導線 | REQ-F-004 / REQ-F-016 / REQ-F-030 | 自社サイトを記事/アーカイブ中心で回す場合の収益化訴求と送客面になる |
| 公開導線 | REQ-F-018 | Phase 1 はシェア、OGP/X Card、人手投稿の接続面として必要。自動投稿は Phase 2 で拡張する |
| 反映安全性 | REQ-F-021 / REQ-F-041 / REQ-F-042 | 記事更新、部分更新、外部編集制御を本番運用できる状態にする |
| 販売ガバナンス | REQ-F-010 | SKU 境界、権限境界、販売条件を崩さない |

自社サイト運用視点での補足は 2 点ある。

1. 機能 23 件に加えて、ローンチ可否は非機能要求にも依存する。特に `REQ-NF-001f`（ページタイプ別性能予算）、`REQ-NF-014`（API/自動化契約）、`REQ-NF-015`（AI運用性/クローラビリティ）、`REQ-NF-017`（LLMO）、`REQ-NF-018`（SEO/WP運用ハザード管理）は、自社サイトが「売る場」かつ「証拠の場」である以上、実質的に欠けてはいけない。
2. X 導線の Phase 配分は本書で固定する。**Phase 1 は共有導線、OGP/X Card、人手投稿のみ**、**Phase 2 で自動投稿、複数アカウント管理、LINE 深い統合、SNS API 認証情報管理へ拡張**する。

### 6.7 グロース KPI

数値目標は PO 確定事項として保留しつつ、計測項目は Phase 1 から定義しておく。

| 層 | 指標 | 目的 |
|---|---|---|
| 流入 | 検索表示回数、検索クリック数、主要流入ページ、指名検索流入 | SEO 主戦場が育っているかを見る |
| 流入 | X フォロワー数、投稿到達、リンククリック、引用 RT 数 | X を継続接点として育てられているかを見る |
| 回遊 | 記事 PV、BLP 到達率、関連記事遷移率、スクロール深度 | 記事から LP へ送客できているかを見る |
| 改善 | CTA CTR、variant 勝率、公開後の改善反映回数 | 自社運用ループが止まっていないかを見る |
| 変換 | テーマ購入数、S1 問い合わせ数、資料請求数、Open Editor Bridge 申込数 | 販売成果を直接測る |
| AI/LLMO | answer unit 到達、AI 由来参照、引用検知、AI 経由 CV | 将来流入の質を測る |
| 運用 | 記事公開本数、更新頻度、rollback 発生数、障害回数 | 運用継続性と品質を測る |

### 6.8 リスクと対応

| リスク | 影響 | 対応方針 |
|---|---|---|
| 自社サイト障害 | サイト停止 = 販売停止 = 証拠停止 | staging、rollback、health check、外形監視、更新前後チェックを標準運用に入れる。販売 LP と証拠表示は事前ビルド済み静的 HTML へ即時切替できる導線を準備する |
| Automation SEO 障害 | 改善ループ停止、記事供給停止、集計遅延 | AGENT NEO 単独での公開/更新経路を維持し、手動運用へ切替可能にする |
| X API / 仕様変更 | 投稿導線の停止、認証失効、運用負荷増 | adapter 層で吸収し、共有導線と OGP を最低ラインとして残す。深い統合は Phase 2 側で拡張管理する |
| SEO スパム判定 | 検索評価低下、ブランド毀損 | AI 大量生成を目的化せず、根拠、更新理由、監修、公開判断を伴う品質ゲートを Automation SEO 側で持つ |
| 公開ダッシュボードの過剰開示 | 顧客情報や内部 KPI の漏出 | 公開値は匿名化・集計化し、顧客単位の数字や機微情報は出さない |
| 計測ドリフト | 販売訴求と実態の不一致 | 自社計測、connector 集計、公開表示の定義を揃え、公開値の算出ルールを固定する |
| 競合模倣リスク | 公開する機能説明から導線設計・改善観点が読み取られ、競合に実装手法が伝わる | 公開する機能説明は原理レベルに留め、内部運用ノウハウ（具体的なプロンプト、variant 生成ルール、改善判断基準）は開示しない |
| 障害時のブランドリスク | 自社サイト障害が「AGENT NEO 製品の品質不足」と読まれる | staging、静的フォールバック導線、障害時の販売 LP 代替経路を準備し、`Built with AGENT NEO` 表示中のサイトが落ちない運用を担保する |
