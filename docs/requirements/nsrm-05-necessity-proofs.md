## REQ-F-001: FSE テーマ基盤

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-001: WordPress FSE（Full Site Editing）がなければ block.json / theme.json による JSON ベース操作の統一基盤が存在せず、AI が JSON で完結操作する入口自体が消える。
- G-003: FSE テーマ基盤がなければ `wp_enqueue_scripts` での page_type 別 asset 振り分けや used_block_css が実装できず、ページタイプ別性能予算の構造的分離が不可能になる。

### counter-example（反例）
この要件がない場合、既存のクラシックテーマ構造で開発を開始したとき、`block.json` による block 宣言・`agentNeo.allowedPageTypes` フィールド・`theme.json` による design token 統一が使えないため、AI が JSON 1 操作で ブロックを安全に追加・変更する統一入口が存在しない。結果として G-001「AI エージェントが JSON のみで完結操作」は実現不可能になる。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
他の REQ-F に統合できるか?
- 独立必須（すべての他 REQ-F が REQ-F-001 の FSE 基盤の上で成立するため、これ自体は他に統合できない）

## REQ-F-002: JSON 操作 API

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-001: REST JSON 操作 API がなければ AI エージェントがテーマ設定・ブロック・レイアウト・CTA を JSON で操作する手段がなく、ビジョンの最上位目標「すべての操作が JSON ベース API で完結」が成立しない。
- G-006: 部分更新（REQ-F-021）・H2 編集（REQ-F-022）・Element Swap（REQ-F-023）・自律 A/B（REQ-F-024）はすべて JSON 操作 API の上に構築される。この基盤がなければ AI 自律最適化ループ全体が崩壊する。

### counter-example（反例）
この要件がない場合、AI が CTA テキストを改善しようとしても書き込む API がなく、WordPress 管理画面での手動操作が必要になる。Automation SEO v2 との「AI がループを回す」運用は人手介在なしでは成立しなくなり、法人版 ¥98,000 の継続価値の核が失われる。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
他の REQ-F に統合できるか?
- 独立必須（REQ-F-003〜REQ-F-043 の大多数が REQ-F-002 を前提とする）

## REQ-F-003: 4 操作面

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-001: AI エージェント（MCP 経由）、自動化スクリプト（WP CLI）、人間管理者（React 管理画面）がそれぞれ同一の JSON 契約で操作できることが「AI が第一級ユーザー」の定義に含まれる。いずれか 1 面を削除すると特定の操作主体が締め出される。
- G-010: Automation SEO v2 は REST API と WP CLI の両面を使うため、どちらかが欠けると v2 との連携最適化が達成できない。

### counter-example（反例）
この要件がない場合、MCP のみを提供したとすると、WP CLI による CLI 自動化（`wp agent-neo ab-test stop`、`wp agent-neo media regenerate-webp`）が失われ、CI/CD パイプラインや緊急停止が手動操作に依存する。法人版の編集ガバナンス（G-012）と自律 A/B の緊急停止が信頼できなくなる。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- REQ-F-002 と密接（JSON 操作 API の操作面の定義であるが、仕様の記述量の観点から分離が妥当）
- 独立必須（4 面の仕様は REQ-F-002 とは別のテスト・実装範囲を持つ）

## REQ-F-004: 個人版収益化ブロック

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-017: アフィリエイターの「出口クリック最大化」が個人版の唯一の CV 指標。Review / Ranking / Comparison / Affiliate CTA / 商品カードがなければ個人版に収益化ツールが存在せず、¥19,800 の価値根拠が消える。
- G-004: 個人版の「結果（CV）を届けるテーマ」は具体的にアフィリクリック数で評価される。このブロック群がなければ CV 直結の設計最上位指標を達成できない。

### counter-example（反例）
この要件がない場合、個人版ユーザーがアフィリエイト比較記事を作ろうとしても専用ブロックがなく、手動 HTML 記述が必要になる。PR 表記自動付与（景表法対応）も失われ、法令コンプライアンス違反リスクが顕在化する。ThemeB/テーマA との差別化（AI 自動配置 + heatmap）も実現できない（G-014）。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- REQ-F-030（個人版販売寄与モジュール強化）と密接（基本ブロック群 vs. 高度 CV モジュールとして分離が妥当）
- 独立必須（コアブロックと拡張 CV モジュールで異なるテストスコープを持つ）

## REQ-F-005: 法人 HP/LP/BLP 三位一体

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-004: 法人版の CV（リード獲得）は HP → LP → BLP の導線で完結する。この三位一体がなければ「全ファネル所有」というペルソナの主な利用シナリオが成立しない。
- G-016: 法人版 ¥98,000 の継続価値は「AI が LP の CTA を部分最適化し CV が上がり続ける」ループに依存する。LP 基盤がなければこのループの発火点がなくなる。

### counter-example（反例）
この要件がない場合、法人ユーザーが HP ブランド入口 → LP（12 セクション）→ BLP（記事 LP）の一貫した導線を構築できず、「問い合わせ・資料 DL を獲得 → 顧客育成」という法人版コアバリューが存在しなくなる。法人版として ThemeB/テーマA と同カテゴリで競うことになり差別化が消える（G-014）。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- REQ-F-012（LP/HP/BLP ブループリント）と密接（F-005 はユーザー向け機能定義、F-012 は JSON 契約・技術設計として分離が適切）
- 独立必須

## REQ-F-006: 計測/A-B/CTA

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-006: AI 自律 A/B テスト（variant 生成 → 配信 → 計測 → 判定 → 自動採用）は section_id / cta_id / variant_id なしでは計測ループが回らない。この基盤がなければ AI 自律最適化の全 4 能力が機能不全になる。
- G-010: Automation SEO v2 の SECTION_METRICS_DAILY / TRACKING_EVENTS テーブルへの書き込みには section_id が必須。計測基盤がなければ v2 連携最適化の中核が失われる。

### counter-example（反例）
この要件がない場合、AI が CTA variant を 2 つ配信しても impression/click の計測 ID がなく、どちらが勝者かを判定できない。「使うほど CV が上がる継続価値」（G-016）は統計的根拠のない当てずっぽうになる。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- REQ-F-024（AI 自律 A/B テスト機構）と密接（F-006 は計測 ID インフラ、F-024 は AI ループ実行部として分離が適切）
- 独立必須

## REQ-F-007: Automation SEO 連携

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-010: Automation SEO v2 との連携がなければ「v2 が引き出しやすい API」を先回り設計する根拠がなく、bulk read / sparse fieldset / outbound webhook 等の最適化 API が不要になる。AGENT NEO は v2 なしで成立しない設計を採用している（§1.2「v2 が AGENT NEO を中央データハブとして利用する想定」）。
- G-006: AI 自律最適化ループの「AI ブレイン（LLM ルーター・ML feedback）」は Automation SEO 側にあり、AGENT NEO がその実行基盤を提供する。連携なしでは AI 自律最適化の頭脳がなくなる。

### counter-example（反例）
この要件がない場合、AGENT NEO は計測 ID を持つ静的テーマに過ぎず、AI が「CTR が低い CTA を自動差替え」する判断基準が得られない。法人版の「買い切り後も CV が上がる」価値命題が消え、¥98,000 の価格正当性が失われる。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- REQ-F-026（v2 連携最適化 API）・REQ-F-027（v2 DB スキーマ直接マッピング）と密接（F-007 は連携の機能要件、F-026/027 は技術的 API 仕様として適切に分離）
- 独立必須

## REQ-F-008: 移行プラグイン

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-007: 既存 WP サイト所有者向けの「テーマ非依存 AI 移行（プラン A/B）」が移行プラグインなしでは実現できない。既存コンテンツを AGENT NEO 標準構造に変換する手段がなければ移行顧客セグメントを獲得できない。
- G-014: 競合（ThemeB/テーマA）からの乗り換えを促すために移行プラグインは差別化要素。乗り換えコストを下げることが競合優位の一部。

### counter-example（反例）
この要件がない場合、既存 ThemeB/テーマA ユーザーが AGENT NEO に乗り換えようとすると投稿・メディア・分類・メニューを手動で再構築する必要があり、移行コストが障壁となり購入を諦める。ターゲットユーザー「移行プラグイン: 既存 WP サイト所有者」セグメントの顧客獲得が不可能になる。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- 独立必須（移行プラグインは別プロダクトとして wp.org 申請対象であり、他 REQ-F と独立したテストスコープを持つ）

## REQ-F-009: 設定エクスポート/インポート

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-001: AI エージェントが JSON のみで完結操作するには、設定を JSON で読み書きする能力が不可欠。エクスポート/インポートがなければ AI による design token の一括更新や設定移行が REST API 経由でも実行できない。
- G-010: Automation SEO v2 が AGENT NEO のトークン設定を参照・変更するユースケース（UC-005: 管理者がブランドトークンを更新する）が成立しなくなる。

### counter-example（反例）
この要件がない場合、ブランドカラーを全 LP に一括反映する操作を AI が行おうとしても、design-tokens.json を JSON Patch で差分レビューして適用するフローが存在せず、CSS 変数の手動編集が必要になる。G-001「JSON 完結操作」が部分的に壊れる。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- REQ-F-025（JSON 統一データモデル）と密接（F-025 はデータモデルの定義、F-009 はその入出力操作として分離が適切）
- 独立必須

## REQ-F-010: ライセンス/パッケージ制御

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-005: 個人版（¥19,800）と法人版（¥98,000）の機能境界がなければ、個人版ユーザーが法人版限定の LP ブループリント・BLP・顧客行動管理を無制限に使えてしまい、価格・機能体系が崩壊する。
- G-009: 商用配布においてライセンス管理機能なしでは不正利用の技術的防止手段がなく、ビジネスモデルが成立しない。

### counter-example（反例）
この要件がない場合、個人版で購入したユーザーが法人版 LP 構造変更 API や A/B テスト承認 gate を使用でき、価格差別化が破綻する。また AI 操作スコープの境界（個人版=記事 CRUD のみ）が機能しないため、個人版 AI が法人向け構造を誤って変更するリスクが発生する。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- 独立必須（ライセンス制御はセキュリティ・課金に関わる独立した横断的関心事）

## REQ-F-011: SEO Core

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-003: ページスピード必達のためには canonical/noindex/OGP が正しく出力されることで SEO 混乱（duplicate content / インデックス肥大化）を防ぐ必要がある。SEO Core がなければ Lighthouse スコアと SEO 健全性が両立できない。
- G-010: Automation SEO v2 は AGENT NEO の SEO メタを読み取り最適化する。SEO Core API がなければ v2 連携の主要ユースケースが成立しない。

### counter-example（反例）
この要件がない場合、記事の canonical が正しく設定されず複数 URL でインデックスが割れる。Automation SEO が SEO メタを参照・更新しようとしても統一 API がなく個別 wp_postmeta を直接操作する必要が生じ、v2 の SEO 最適化ループが壊れる。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- REQ-F-007（Automation SEO 連携）と密接（SEO Core は AGENT NEO 側の管理、F-007 は v2 との同期ブリッジ）
- 独立必須

## REQ-F-012: LP/HP/BLP ブループリント

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-006: 要素差し替え（Element Swap: blueprint_id swap）は LP ブループリントが存在して初めて可能になる。ブループリントがなければ LP 全体を blueprint_id 単位で差替える AI 自律最適化の一部が失われる。
- G-010: v2 の WP_PAGES テーブルに AGENT NEO の page_type / template を露出するには、ブループリントが section_id / cta_id / offer_id / service_id を持つ JSON 契約として定義されている必要がある。

### counter-example（反例）
この要件がない場合、複数サービスを持つ法人（service_id 3 件以上）が HP Gateway から各サービス LP へ正しく誘導するルーティングが構築できない。Automation SEO が「このサービス向けの LP の Hero セクションを変更したい」という操作を service_id で絞り込めず、全 LP に影響するリスクがある。

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- REQ-F-005 と密接（F-005 はユーザー機能要件、F-012 はその JSON 契約・技術実装仕様）
- 独立必須

## REQ-F-013: 法人版リード獲得

### 削除可能性評価
✓ 必須（削除不可）

### 統合可能性評価
- REQ-F-031（法人版販売寄与モジュール強化）と密接（F-013 は標準フォーム基盤、F-031 は Multi-step form 等の CV 強化拡張として分離が適切）
- 独立必須

## REQ-F-014: 法人版顧客行動管理

### necessity_proof（必要性証明）
削除すると失敗するゴール:
- G-016: 法人版の「買い切り後も CV が上がる継続価値」はリードスコアリングと健康度モニタリングによって「どのリードに優先アプローチするか」が可視化されることで実現する。行動管理なしでは「獲得したリードをどう育成するか」が不透明になる。
