# 運用・セキュリティ・可用性・更新性分析

## 結論

見える。現状のAGENT NEO設計には、セキュリティ、プラグイン依存、性能、AI操作ガードの断片はすでにある。ただし、商用テーマとして売るなら「実装時に気をつける」では弱い。運用、更新、互換性、障害時の劣化、プラグイン追加時の衝突を、JSON契約と管理画面の診断機能として製品化する必要がある。

AGENT NEOでは次をP0にする。

| 契約 | 目的 |
|---|---|
| `compatibility-matrix.json` | WP/PHP/DB/ブラウザ/主要プラグインの対応範囲 |
| `update-policy.schema.json` | 更新チャネル、互換性チェック、ロールバック、DBマイグレーション |
| `security-baseline.schema.json` | nonce、capability、sanitize、escape、SSRF、XSS、権限境界 |
| `plugin-conflict-rules.json` | SEO、キャッシュ、フォーム、GTM、ブロック拡張との衝突検出 |
| `availability-profile.json` | 外部依存障害時のfallback、劣化モード、SLO |
| `ops-runbook.schema.json` | 更新前後チェック、障害時対応、復旧手順 |
| `observability-profile.json` | metrics、logs、alerts、health check、管理画面診断 |

## R0: 証拠

### SWELL

| 観点 | 証拠 | 読み取り |
|---|---|---|
| 動作環境 | `style.css` に `Requires at least: 5.6`、`Requires PHP: 7.3.0` | 下限互換を広く取り、導入可能性を優先 |
| 起動時チェック | `functions.php` 先頭で `lib/check_environment.php` を読込 | WP/PHP下限を早期判定 |
| 管理者限定処理 | `functions.php` で `current_user_can( 'manage_options' )` のときだけ activate/update を読込 | 更新・ライセンス処理を管理者に寄せる |
| 更新チェック | `lib/update.php` で Plugin Update Checker を利用 | 自社配布テーマの更新チャネルを持つ |
| 更新後処理 | `lib/updated_action.php` で旧バージョン比較、DB更新、キャッシュ削除 | 更新時の後方互換・マイグレーションを持つ |
| WPバージョン分岐 | `classes/Utility/Status.php` の `wpver_is_above()` | WPコア差分に合わせてUI/APIを切り替える |
| セキュリティ | `activate.php` の nonce確認、sanitize、safe redirect | 管理操作はnonce/sanitizeを使う |
| 出力安全 | 多数の `esc_html`、`esc_attr`、`esc_url`、`wp_kses` | 出力contextごとのescapeが基本方針 |

### JIN:R

| 観点 | 証拠 | 読み取り |
|---|---|---|
| 動作環境 | `style.css` に `Requires at least: 5.9.1`、`Requires PHP: 7.0` | SWELLよりWP下限は新しめ、PHP下限は古め |
| 更新チェック | `functions.php` で `theme-update-checker.php` と更新JSONを利用 | 自社配布テーマ更新機構を持つ |
| セッション | `template_redirect` で `session_start()` | テーマでセッションを持つのは可用性/キャッシュ互換上のリスク |
| 出力安全 | `esc_attr`、`esc_url`、`sanitize_title` 等を利用 | escape/sanitizeはあるが、巨大テンプレート構造で監査しにくい |

| 契約 | SWELL | JIN:R | AGENT NEO採用 |

| 管理者限定処理 | あり | 一部 | 採用 |
| WPバージョン分岐 | あり | 弱い | 採用 |
| プラグイン衝突検出 | 限定的 | 限定的 | 大幅強化 |
| 外部依存障害時fallback | 限定的 | 限定的 | 大幅強化 |
| SLO/監視 | ほぼなし | ほぼなし | AGENT NEOの差別化要素にする |

## R2: AGENT NEO 運用品質設計

### 1. WP/PHP/DBバージョン対応

公式要件では、WordPress.orgはPHP 7.2.24+やMySQL 5.5.5+でも動作するとしつつ、それらはEOLでセキュリティリスクがあるため、PHP 7.4+、MariaDB 10.6+ または MySQL 8.0+、HTTPSを推奨している。2026-03-10にはWordPress 6.9.2がセキュリティリリースとして公開され、2026-04-22時点でWordPress 7.0のリリース日は2026-05-20予定に更新されている。

AGENT NEOの方針:

| 区分 | 初期方針 |
|---|---|
| 最低WP | `6.6+` を維持。ただし発売時点で `tested up to` を最新安定版へ更新 |
| 推奨WP | 最新安定版の1世代以内 |
| 最低PHP | `8.1+` |
| 推奨PHP | ホスティングで安定して使える最新LTS寄り |
| DB | MySQL 8.0+ / MariaDB 10.6+ 推奨 |
| HTTPS | API/ライセンス/外部送信はHTTPS必須 |
| WP 7.0対応 | Real-Time Collaboration、metabox互換、Gutenberg API変更を重点検証 |

### 2. 更新性

参照テーマは自社更新JSONでテーマ更新を実現している。AGENT NEOでは単なる更新通知では足りない。AI操作・SEO・計測・Blueprintがあるため、更新前診断とロールバック可能性が必要。

| 要素 | 設計 |
|---|---|
| 更新チャネル | `stable`、`security`、`beta`、`enterprise` |
| 更新前チェック | WP/PHP/DB、必須plugin、schema version、互換plugin、バックアップ有無 |
| 更新後処理 | DB migration、schema migration、cache purge、contract revalidation |
| rollback | 直前バージョン、直前schema、設定export、migration logを保持 |
| 破壊的変更 | major versionのみ。管理画面で明示承認 |
| セキュリティ更新 | minor/patchで即時適用を推奨 |

採用しない実装:

| 参照実装 | 理由 | AGENT NEO方針 |
|---|---|---|
| 更新HTTPで `sslverify=false` | 中間者攻撃や改ざん検知の観点で弱い | HTTPS検証必須、更新manifest署名、hash検証 |
| テーマ内で広範囲に `session_start()` | キャッシュ、CDN、ページ表示可用性を壊しやすい | セッション非依存。必要ならCore Plugin側で短命token/nonce |
| 更新後の暗黙migration | ユーザーが失敗時に戻せない | preflight、migration log、rollback/exportを必須化 |

### 3. セキュリティ

WordPress REST APIのcookie認証ではnonceがCSRF対策として使われ、操作には適切なcapabilityも必要になる。nonceは権限そのものではないため、AGENT NEOでは必ず `nonce + capability + package scope + schema validation` をセットで扱う。

| 領域 | 必須ガード |
|---|---|
| REST書き込み | `X-WP-Nonce`、`permission_callback`、capability、rate limit |
| MCP | localhost/token、path allowlist、dangerous operation confirm |
| WP CLI | dry-run default、`--yes`明示、capability相当の実行ユーザー確認 |
| AI生成HTML | `wp_kses` allowlist、script禁止、URL検証 |
| 外部URL取得 | SSRF対策、private IP拒否、timeout、redirect制限 |
| SEO変更 | canonical/noindex/robots変更はcritical warning |
| 計測API | 署名、bot filter、匿名ID、PII禁止 |
| ログ | token、license key、email、IPフル値をそのまま残さない |

### 4. 可用性と劣化モード

テーマはSaaS本体ではないが、AGENT NEOは外部連携が多い。したがって、外部サービスが落ちても表示・基本CTA・基本SEOは維持する。

| 障害対象 | 通常影響 | fallback |
|---|---|---|
| Automation SEO | AI提案/同期停止 | 手動編集、ローカルqueue、再送 |
| seo-tool-connector | 詳細計測停止 | ローカル軽量計測 |
| ライセンスサーバー | 更新/上位機能判定が不安定 | grace period、既存有効状態キャッシュ |
| GA4/GTM | 外部計測停止 | 表示には影響させない |
| CRM/フォーム | 送信失敗 | 外部フォームリンク、メール/電話CTA |
| キャッシュplugin | 最適化競合 | compatibility mode、AGENT NEO asset policy優先 |

SLO案:

| 指標 | 目標 |
|---|---:|
| 公開ページ表示可用性 | `99.9%` |
| JSON操作成功率 | `95%+` |
| 計測イベント欠損率 | `1%` 未満 |
| 更新後fatal error | `0` |
| 重大セキュリティ脆弱性対応 | Critical 24h / High 7d |

### 5. プラグイン追加への対応

AGENT NEOは「外部プラグインを禁止するテーマ」ではなく、追加されたプラグインを検出して衝突リスクを説明するテーマにする。

| プラグイン種別 | 主な衝突 | 対応 |
|---|---|---|
| SEO | title/canonical/OGP/schema重複 | `SeoConflictDetector` で出力優先順位を選ばせる |
| Cache/Optimize | JS遅延、critical CSS、lazyload二重化 | `PerformanceCompatibilityMode` |
| Form/CRM | CTA計測漏れ、外部送信同意 | `FormAdapter`、外部送信data map |
| Security | REST/MCP/WP CLI遮断 | health checkで検出し、必要routeを案内 |
| Block拡張 | block.json/asset衝突 | namespace確認、asset budget監査 |
| Analytics/GTM | 二重計測、同意漏れ | tag governance、consent gate |

### 6. 運用画面

法人版では「運用できる」こと自体が価値になる。管理画面に次を置く。

| 画面 | 内容 |
|---|---|
| Health | WP/PHP/DB/HTTPS/cron/REST/loopback/権限 |
| Updates | 現在版、更新可能版、互換性、rollback準備 |
| Security | nonce/API/権限/外部送信/ログマスク/危険設定 |
| Plugins | 衝突検出、adapter状態、fallback状態 |
| Integrations | Automation SEO、seo-tool-connector、GA/GTM、CRM |
| Logs | AI操作、更新、migration、計測失敗、同期失敗 |
| Runbooks | 更新手順、障害対応、復旧、サポート提出情報 |

## R3: 差分

| 現状 | 不足 | ルーティング |
|---|---|---|
| L1にセキュリティ/可観測性/依存度はある | 運用・更新性・可用性が独立要件になっていない | L1 |
| L2にSTRIDE/監視ログはある | SLO、劣化モード、更新チャネル、plugin衝突ルールが弱い | L2 |
| package matrixに依存ガードはある | update/ops/security/availability契約が足りない | package |
| 参照テーマに更新機構はある | 署名、rollback、contract migrationの設計が必要 | L3 |
